# Интеграция outbox S4

Создайте один `createOfflineOutbox` на процесс, передайте ему
`createSQLiteOutboxStorage({ transaction })`, `createOutboxTransport({ authFetch })`,
`isOfflineSessionCurrent` и `createOfflineId` из S1 в качестве `createId`.
Модуль принимает сессию явно в каждом вызове. Данные принадлежат паре
`{origin, userId}`. Повторный вход того же владельца продолжает его очередь.
Чужой аккаунт или origin не читает эту очередь. При закрытии сессии отмените
её отправку через `cancelDrain(session)` и сбросьте её UI и таймеры.

## Транзакция S1

`transaction(session, work)` возвращает Promise с результатом синхронного
`work(sql)`. После получения `offlineDatabase()` проверьте текущую сессию.
В `db.withTransactionSync` проверьте строку `activation` по
`JSON.stringify([session.owner.origin, session.owner.userId])` и
`session.activationId`, затем вызовите `work(db)`. Проверьте актуальность
поколения перед возвратом результата. Outbox использует `runSync` и
`getFirstSync`. Таблицы `outbox_*` создаются при первой транзакции без
изменения `PRAGMA user_version`. Сеть выполняется после завершения
транзакции. Для rollback исключение из `work` должно выйти из callback SQLite.

## Оценки и обновление каталога

- Обработчики лайка и дизлайка передают явное `like`, `dislike` или
  `neutral` в `setRating(session, trackId, rating)`. После commit примените
  результат к UI, локальным кандидатам Волны и причинам хранения избранного.
  Решения о рейтинге должны использовать актуальный локальный overlay. Запрос
  к brain может выполняться в фоне. Снимок избранного или Волны не должен
  стирать новую локальную оценку, пока её ревизия ожидает отправки.
- `getRating(session, trackId)` возвращает `{rating, revision, state, operationId}`
  или `null`. `pending` пригоден для overlay после рестарта.
  `synced` подтверждает доставку команды. Свежие Favorites/Dislikes после
  доставки дают актуальное серверное состояние, в том числе более позднюю
  правку на другом устройстве. Применяйте обновление только к сохранённой
  сессии и с учётом ревизий, которые появились во время refresh.
  `missing` завершает действие удалённого трека, `failed` позволяет показать
  терминальную ошибку. Поле ревизии локальное и увеличивается при явной оценке.
- Ставьте `drain(session)` при открытии сессии, возврате приложения на
  передний план, восстановлении сети и после новых локальных записей.
  Дождитесь завершения drain перед обновлением избранного и будущей очереди,
  учитывая оставшиеся `pending` оценки. Пока один drain работает, заявка на
  повторный запуск после нового commit должна сохраниться в планировщике
  интеграции. `nextDueAt` задаёт ближайшее время следующей пачки, включая
  немедленное продолжение после лимита пачки. `unauthorized` ждёт нового
  допуска, штатный `authFetch` закрывает текущую авторизацию при 401.
  События `settled` содержат исход конкретных элементов, без рейтинга и без
  изменения проекции на стороне UI. Отбрасывайте результаты закрытой сессии.
- Замените прямые мутации оценок и отправку wave `like` из iOS.
  Сервер атомарно меняет существующие Favorites/Dislikes, а receipt операции
  позволяет повторить исходную команду после потери ответа. Повтор не
  воспроизводит изменение поверх более поздней серверной команды.

## Ingestion из плеера

- В `usePlayerController` перенесите запись истории с выбора трека на
  подтверждённый нативный статус текущего источника. Используйте идентичность
  источника/запроса, принятую в `playbackCoordinator`. Требуйте подтверждённого
  старта и первого фактического движения позиции во время playing без
  buffering. Не используйте выдачу URL, результат replace, Play intent,
  restore, preload или скачивание.
- Один раз на фактический эпизод создайте `playbackId` через
  `createOfflineId()` и зафиксируйте UTC `occurredAt` в момент подтверждения
  воспроизведения вместе с `trackId` и `context` (`wave` или `manual`).
  Передайте этот объект в `recordStarted(session, play)`. Сохраните объект на
  эпизод. Пауза, resume, seek и замена источника для recovery того же эпизода
  сохраняют ID. При фактическом повторном старте после finish выдается новый.
  Восстановление только последнего трека после завершения процесса создаёт
  эпизод при новом подтверждённом старте.
- На подтверждённом `didJustFinish` или при пользовательском уходе с трека
  с фактическим прогрессом вызовите `recordOutcome(session, {...play, outcome,
listenDurationMs, trackDurationMs})` один раз. Обрабатывайте finish без
  следующего трека и в repeat-one. Накапливайте доказанный прогресс, исключая
  скачки от seek, паузу, буферизацию и отброшенные source events.
  Отмена загрузки, отказ плеера или смена сессии не создают skip.
  Для прерванного процессом эпизода history остаётся слабым start-сигналом.
  Отдельный `recordPlayStart` артиста сохраняет свой счётчик.
- История и terminal feedback повторяют точный payload и используют один
  playback ID, context и timestamp первого воспроизведения. Backend
  сопоставляет их независимо от порядка и задержки доставки. Outcome
  заменяет start в taste. Удалите старые прямые history/skip/finish вызовы
  при подключении S4, иначе старые вызовы не имеют общего playback ID.

## Совместимость

S4 использует PUT на ресурсах rating, history и wave feedback. Прежние
POST/DELETE продолжают работать для старых клиентов. PUT защищает от
случайного legacy append, если iOS подключится к старому brain.
Отсутствующий современный маршрут (405 или обычный 404) оставляет запись
для повтора. 404 с подтверждённым ответом «Трек не найден» завершает
запись. Повторяемые сбои остаются в очереди с сохранённой паузой между
попытками. 429 ставит паузу по классу операций и учитывает `Retry-After`.

## Подключение штатного плеера и потребителей

`usePlayerController` запускает `startOutboxSync()` при монтировании и
отписывается при размонтировании. `runtime.js` отслеживает активацию S1,
возврат приложения на передний план и состояние сети. На закрытии сессии
отменяются отправки, чтение ответов и таймер. В актуальной сессии GET
Favorites/Dislikes после drain сохраняет серверную основу, а SQLite оставляет
поздние ревизии в overlay. Штатная Волна обновляет только будущие рекомендации
и сохраняет вручную поставленные треки и текущий нативный источник.

J2 использует `setLocalRating(session, track, rating)` для всех действий
с оценкой и `projectFavoriteTracks(session, tracks)` перед отображением снимка
и сверкой причин хранения. `getRatingOverlay(session)` возвращает
`{trackId, track, rating, revision, state, operationId}` для ещё не
согласованных оценок. Поле `track` содержит только данные для отображения.
Для синхронного применения переданного overlay доступен
`overlayFavoriteTracks(tracks, ratings)`. Снимок следует проецировать после
каждого чтения, в том числе если экран получил его до последнего commit.
Перед самостоятельным GET Favorites вызовите
`const isCurrent = captureFavoritesSnapshotGuard(session)`. После ответа
и наложения overlay проверяйте `isCurrent()` перед обновлением UI, снимка
или retention. Ответ может прийти после более свежего снимка S4.

S3 может вызвать `getLocalDislikeIds(session)` перед подбором локальных
кандидатов. Он возвращает `Set<string>` из последнего сохранённого серверного
Dislikes и локальных оценок. Если серверная часть уже загружена вызывающим
кодом, можно применить `overlayDislikeIds(dislikes, ratings)`.

`subscribeOfflineIndex` из `offline/session.js` передаёт следующие события
с захваченной `session`.

- `rating` с `entry` после локального commit. J2 сразу обновляет библиотеку
  и причины хранения, S3 исключает локальный дизлайк.
- `rating-overlay` с `overlay` и сохранённым `snapshot` при открытии.
- `ratings-refreshed` с `favorites`, `dislikes` и текущим `overlay` после
  успешных GET. J2 может вычислить разницу для retention по этим данным.
- `outbox-settled` с `settled` после каждой завершённой пачки.
- `interactions-drained` после завершения drain и обновления снимка.
  S3 запрашивает будущую очередь и фильтрует оставшиеся дизлайки. Событие
  также публикуется после открытия, возврата связи или на передний план.

Используйте `isOfflineSessionCurrent(session)` после асинхронных операций.
Снимок `Favorites` в offline index хранит серверную основу. Pending-оценки
и их метаданные сохраняются в таблицах S4 и накладываются при чтении.
