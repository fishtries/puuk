Проверить реальные процессы и менеджер сервисов на сервере, локальные heavy_worker и SFTP writers. Не выводить env/токены в отчёты.
3. В согласованном окне приостановить старые writers: API, бот, сканеры, local heavy_worker. Снять свежий согласованный SQLite backup через backup API; сохранить прежний код/конфигурацию, schema/counts, integrity/FK и права доступа. Одна копия main.db при активном WAL недостаточна.
4. Выполнить `./deploy.sh` только после подтверждённого состава выпуска. Корневой скрипт делегирует в `brain/deploy.sh`: backend restart выполняется **до** синхронизации бота. Поэтому writers должны быть остановлены заранее, трафик и импорт оставаться закрыты до совместимого startup всех компонентов. Fallback `pkill -9 ... || true` не запускает сервис и не подтверждает успешный restart. Не использовать `--delete`/`--install` без соответствующей необходимости.

## Восстановление

Ошибочное исправление данных отменяется условным `undo` его production operation ID от admin; новая правка после apply должна дать конфликт, а не потеряться. Для ошибки кода предпочтителен совместимый roll-forward. Возврат старых binaries после schema12 небезопасен: они игнорируют override. Полное восстановление требует остановки writers и согласованного набора прежнего кода/DB/конфигурации с отдельным сохранением поздних данных. Проверка backup на копии выше не доказывает автоматическое слияние поздних production записей.
