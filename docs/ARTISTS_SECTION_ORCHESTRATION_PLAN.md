# План оркестрации: раздел артистов Puuk

## 1. Назначение документа

Документ задаёт исполнимый план для координатора, который ведёт работу с помощью senior- и junior-агентов. Он описывает продуктовую цель, известную архитектуру, порядок задач, владение файлами, критерии приёмки и правила эскалации. Это план реализации, а не утверждение, что задачи уже выполнены.

Координатор отвечает за итоговый контракт, разбиение задач, последовательность зависимостей, интеграцию и независимую приёмку. Исполнители отвечают только за явно назначенные задачи и перечисленные им области владения.

## 2. Цель продукта

Добавить в Puuk раздел артистов. Первый приоритет — iOS; веб-клиент сейчас не менять. Пользователь открывает страницу артиста из общего поиска или нажатием на имя исполнителя в плеере. Страница артиста содержит:

- изображение артиста, загружаемое вручную;
- популярные треки, отсортированные от наиболее популярных к менее популярным;
- дискографию артиста;
- поиск по каталогу артистов.

В каталоге нет отдельной нижней вкладки iOS. Навигация внутренняя: открыть экран артиста из существующих сценариев и вернуться с сохранением контекста поиска. После приёмки iOS отдельным этапом перенести согласованный сценарий в веб.

## 3. Принятые решения и границы

### Принято пользователем

- Раздел нужен в обоих клиентах, но текущая задача сосредоточена на iOS.
- Веб в первой реализации не менять.
- Артист — отдельная внутренняя страница, доступная из поиска и по нажатию на исполнителя в плеере.
- На странице нужны популярные треки, дискография и изображение артиста.
- Изображение загружается вручную.
- Описание и внешние ссылки не нужны.
- Новую нижнюю вкладку iOS не добавлять.
- Каталог общий для пользователей.
- Каталог должен иметь обычный поиск; бесконечную прокрутку добавлять не нужно.
- Отдельная точка входа в полный каталог артистов не утверждена; явно утверждены переходы из общего поиска, плеера и страницы альбома.
- Если у трека нет имени артиста, страницу для него не создавать.
- Не включать compilation/Various Artists как специального артиста.
- По нажатию на артиста в iOS-поиске открывать страницу артиста, а не повторять поиск.
- На странице альбома исполнитель кликабелен; имена артистов в строках треков пока не делать кликабельными.
- Визуальный ориентир — Apple Music.
- Пользователь указал «просмотры» как показатель популярности.
- Пользователь согласился с объединением сущности артиста из исполнителя трека и исполнителя альбома.

### Не решено: блокирующие продуктовые вопросы

До утверждения API и ранжирования координатор должен выяснить у пользователя:

1. Что именно считать «просмотрами» для популярности треков: число запусков/прослушиваний треков, число открытий страницы артиста или другой сигнал. Контекст подразумевает популярность треков; не подменять просмотры страницами без подтверждения.
2. Какое окно учитывать для популярности: всё время или период. Если ответа нет, предложить «за всё время» и дождаться подтверждения.
3. Как трактовать разные написания одного имени, например `DJ Arbuz` и `Диджей Арбуз`. Отдельные записи без alias-management — безопасный временный вариант, но согласие пользователя явно не получено.
4. Как ранжировать треки при нулевых просмотрах и равных значениях; предпочтительный стартовый tie-breaker — имя трека, затем ID, детерминированно.

Не блокирующие решения, которые координатор может принять консервативно и зафиксировать в реализации:

- сортировка альбомов: год по убыванию, затем название; альбомы без года после альбомов с годом;
- каталог артистов: алфавитная сортировка без учёта регистра, без отдельного UI алфавитных секций;
- полный каталог без пагинации и бесконечной подгрузки, но не загружать полные DTO треков; выдавать только компактные artist DTO;
- пустая строка артиста исключается из каталога;
- в compilation не создавать сущность «Various Artists»; артистов конкретных треков сборника можно включить по их собственным тегам.

Не трактовать молчание как подтверждение изменения поведения существующих экранов. Записывать дополнительные продуктовые решения в задачу/отчёт и, если они общие для платформ, в `docs/design/DESIGN.md`.

## 4. Исходный код и известные точки интеграции

Перед делегированием координатор повторно проверяет актуальный checkout. Первичный осмотр обнаружил:

- Backend — FastAPI + SQLite; миграции в `brain/migrations/`, схемы и репозитории в `brain/repositories/`.
- `brain/repositories/tracks.py::search_all` уже возвращает artists, сгруппированных по точному `tracks.artist`, с `track_count`, `album_count` и `cover_track_id`; это только поиск, не полный каталог и не detail API.
- `brain/routers/search.py` сериализует search artists с `name`, счётчиками и cover URL.
- Альбомы являются отдельными сущностями (`albums`), имеют `album_artist`, каталог `/api/albums` и detail `/api/albums/{id}`.
- Общая iOS-навигация находится в `app/ios/puuk-ios/navigation/RootNavigator.js` и `MainTabs.js`; существующие экраны лежат в `features/`.
- iOS-поиск `features/search/SearchScreen.js` уже загружает массив `artists`, но `handleArtistPress` повторяет поиск вместо перехода.
- iOS-плеер находится в `components/FullPlayerModal.js` и `components/fullplayer/`; точный компонент интерактивного artist label требуется подтвердить на текущем коде.
- iOS API transport: `shared/api/api.js` (`authFetch`), медиа/обложки — `shared/media/` и API-кэш; проверить актуальные exports и upload conventions.
- iOS экран альбома: `features/albums/AlbumScreen.js`; он уже использует `/api/albums/{id}`.
- `app/ios/puuk-ios/AGENTS.md` требует перед изменениями кода читать документацию именно Expo SDK 58: `https://docs.expo.dev/versions/v58.0.0/`.
- UI-решения: `docs/design/DESIGN.md`, платформенная реализация — `docs/design/ios.md`.

Это ориентиры, а не полный аудит. Senior обязан проверить вызовы, DTO, миграционный порядок и состояние рабочей копии перед финализацией контракта.

## 5. Роли и полномочия

### Координатор / ведущий агент

- Уточняет блокирующие продуктовые вопросы и фиксирует ответы.
- Создаёт Orca Run/Tasks/Dispatch (или эквивалентный supervised workflow), задаёт зависимости и исполнителей.
- Проверяет рабочее дерево, принимает ownership-модель и не допускает конфликтующих правок.
- Утверждает API, модель данных, event contract для просмотров и UX-потоки до реализации.
- Интегрирует результаты, самостоятельно запускает обязательные проверки, проверяет diff и критерии.
- Даёт отдельную review-задачу агенту, который не реализовывал проверяемую часть, если риск этого требует.
- Не принимает `worker_done` как доказательство качества без проверки артефактов.

### Senior agent

Senior владеет архитектурой и рискованными границами:

- backend/API и модель сущности артиста;
- определение и корректность метрики просмотров/популярности;
- модель хранения и безопасность upload;
- интеграционный контракт backend ↔ iOS;
- навигационная модель и state restoration;
- миграционная совместимость, производительность каталога, транзакции и ошибки;
- финальный дизайн реализации и разрешение конфликтов между областями.

Senior может реализовать критический вертикальный срез. Не передавать junior архитектурные решения, которые ещё не утверждены.

### Junior agent

Junior выполняет ограниченные, проверяемые задачи после утверждения контрактов:

- UI-компоненты каталога/страницы по готовым DTO и navigation contract;
- компактные API client functions и типы по утверждённой схеме;
- тесты для согласованного поведения;
- отдельные небольшие изменения в конкретном экране с точным списком файлов;
- документацию реализации и отчёт проверок.

Junior не должен самостоятельно менять схему API, вводить alias semantics, выбирать систему ранжирования, редактировать миграции или общие навигационные границы без отдельного одобрения senior/координатора.

### Reviewer

Проверяет конкретный diff и observable acceptance независимо от автора. Может быть senior или отдельный reviewer другой модели. Проверяет отсутствие регрессий, безопасность, совместимость и воспроизводимость результатов. Не расширяет область задачи без согласования.

## 6. Правила запуска и совместной работы

1. Использовать механизм оркестрации, подходящий текущей сессии; перед Orca прочитать `docs/ORCHESTRATION.md` и version-matched skill установленной версии.
2. Каждая Task должна быть самодостаточной и содержать `Target`, `Change`, `Constraints`, `Ownership`, `Acceptance`, `Report`.
3. В текущем checkout уже могут присутствовать пользовательские изменения. Перед стартом сохранить `git status --short`, изучить пересечения с каждым target и явно перечислить их в Run. Не переносить и не перезаписывать чужие изменения.
4. Проверить модель и launcher по фактической конфигурации. Роль junior сама по себе не гарантирует выбор более дешёвой модели.
5. Параллелить только независимые задачи с непересекающимся ownership. Любые два агента не редактируют один файл одновременно.
6. Предпочтительно использовать отдельные worktrees для параллельных source changes. При `current` каждый агент обязан работать только в allowlist.
7. Не запускать iOS реализацию до прочтения точной документации Expo SDK 58 и утверждения navigation/API contract.
8. Данные популярности, не имеющие исторического backfill, должны явно показывать корректный cold-start порядок; нельзя придумывать просмотры из лайков, открытий страниц или случайного SQL-порядка.
9. Не выполнять деплой и не менять production data в рамках реализации без отдельного запроса владельца.
10. При блокирующем вопросе агент эскалирует координатору через предусмотренный механизм и не выбирает скрыто продуктовый вариант.

## 7. Этапы и зависимости

### Этап 0. Baseline и продуктовые решения

**Владелец:** senior + координатор. **Junior:** не назначать до выдачи ограниченной инвентаризационной задачи.

**Работа:**

- записать baseline `git status`, изучить текущие незакоммиченные изменения;
- аудит текущего player playback/event logging, history/favorites/interaction tables, общей модели пользователей и album APIs;
- выяснить точный смысл просмотров, окно рейтинга, cold start и политику вариантов написания имени;
- определить, нужна ли сущность артиста в SQLite: ручное изображение требует стабильного места хранения и идентичности; не привязывать картинку к нестабильной строке без рассмотрения нормализации;
- зафиксировать источники artist membership: `tracks.artist`, `albums.album_artist`, алиасы (если принято), compilation policy;
- уточнить единицы доступности: общий каталог подтверждён, следовательно artist catalog/detail не фильтруются по user ID; персональный сигнал популярности, если он выбран, должен определить aggregation/privacy semantics.

**Выходные артефакты:** решение-заметка с API DTO, storage model, ranking formula, sort rules, upload limits/allowed image types, navigation route contract и список файлов-владельцев.

**Gate 0:** senior и координатор согласовали все blocking product questions. Если нет, продолжать только независимое read-only исследование и не фиксировать необратимый контракт.

### Этап 1. Read-only техническая разведка

**Параллельная волна; отдельные read-only Tasks:**

- **Junior A, backend inventory:** запросить точные функции чтения/записи истории воспроизведения, SQL схемы и тестовые patterns; вернуть пути, SQL contracts, отсутствующие возможности. Ничего не менять.
- **Junior B, iOS navigation/UI inventory:** проследить root stack, album route, SearchScreen artist card/handler, player artist text, album artist text, state restoration и связанные тесты. Ничего не менять.
- **Junior C, media/upload inventory:** найти существующие image upload/storage/static serving patterns, permissions и cover API behavior. Ничего не менять.
- **Senior, synthesis:** сопоставить результаты, проверить риски и выбрать минимальный вертикальный контракт.

**Приёмка:** отчёты содержат точные пути/символы и воспроизводимые ссылки на код; предположения отделены от фактов; рабочее дерево неизменно.

### Этап 2. Контракты и проектирование

**Владелец:** senior. Координатор утверждает.

Определить до кода:

- `ArtistDTO`: стабильный ID, display name, artwork URL/version, track/album counts и любые поля, нужные списку; не раскрывать локальные file paths.
- artist catalog: сортировка, поиск (case-insensitive по принятой нормализации), лимит/максимальный ответ. Поскольку бесконечная прокрутка запрещена, endpoint отдаёт полный компактный список либо UI использует явную ограниченную загрузку; при 10k+ имён измерить размер ответа и принять решение до реализации.
- artist detail envelope: artist, popular tracks, albums; определить, возвращаются ли все треки в популярных или фиксированный top-N. Рекомендация для согласования: ограниченный top-N популярных треков плюс все альбомы; пользователь должен подтвердить число/механику, либо экран может показывать сортируемый полный список без бесконечной подгрузки.
- ranking endpoint semantics: источник событий, уникальность событий, защита от повторного события на playback progress callbacks, окно и порядок tie-break.
- изображение: upload transport (multipart предпочтительно), MIME allowlist, максимальный размер, декодирование/валидация, безопасное имя, атомарная замена, удаление, cache invalidation/versioning, auth/authorization и error DTO.
- стабильный artist identity и дубликаты; если сохраняются разные написания как отдельные записи, определить case/whitespace normalization, чтобы одна и та же строка не размножалась от технических пробелов.
- iOS routes: ArtistCatalog/ArtistDetail или эквивалент; параметры должны нести stable artist ID, а не только имя. Вход из player/detail/search и return behavior.
- API compatibility: существующий `/api/search` сохраняет контракт; artist search result дополняется `artist_id` только если server умеет дать стабильную идентичность.

**Выход:** короткий design/ADR документ или утверждённая секция в orchestration report; OpenAPI/DTO sketch; файл ownership map; список миграций и тестов.

**Gate 1:** никакой UI/DB implementation до утверждения senior и координатором. Пользовательские незакоммиченные изменения не считаются частью контракта.

### Этап 3. Backend vertical slice

**Владелец:** senior backend. Junior может получить изолированный тестовый или сериализационный подэтап после стабилизации API.

**Scope:** migrations/repository/service/router/serialization/tests для каталога, поиска, detail, популярности и изображения согласно Gate 1.

**Обязательные инварианты:**

- миграция идемпотентна и совместима с существующей SQLite; все тесты изолированы через `PUUK_DB_PATH`;
- SQL не загружает полную таблицу треков на каждый catalog request; индексы/запросы оправданы измерением и планом;
- корректная группировка артиста из треков и album_artist не дублирует один релиз в дискографии;
- пустой artist name исключён; Various Artists не становится специальной записью;
- порядок детерминирован, null/year handling определён;
- public DTO не содержит file paths, токенов, абсолютных путей или пользовательских приватных полей;
- image update/remove атомарны относительно БД и файла, переживают retry и не удаляют прежнее изображение до успешной замены;
- event ingestion учитывает повторные вызовы плеера, событие фиксируется по документированным правилам, replay/duplicates не надувают счётчик;
- существующий поиск `/api/search` и альбомные endpoint остаются обратно совместимыми.

**Тесты:** repo/service/router tests на пустой каталог, одинаковое имя/нормализацию, несколько track artist, album_artist при отличающемся track artist, compilation, пустого артиста, счётчики и порядок; популярность с нулём/несколькими событиями/дубликатами/равенством; upload valid/invalid/oversize/remove/failure/authorization; HTTP 404/validation; миграция на legacy fixture.

**Приёмка:** тесты backend проходят, `git diff --check` чистый, миграция протестирована на старой схеме и повторном запуске, запросы и индексы проверены на репрезентативных фикстурах.

### Этап 4. iOS API client и типы

**Владелец:** junior после Gate 1 и фиксации backend contract. **Reviewer:** senior.

**Scope:** отдельные API functions/types для catalog/search/detail/artwork mutation, нормализация URL и ошибки по установленным conventions.

**Ownership:** точные allowlist файлов в Task; не редактировать navigation/screens/player. Тесты API client могут принадлежать той же задаче, но backend files — нет.

**Приёмка:** успешные DTO преобразуются предсказуемо, HTTP/сетевые/abort ошибки видимы вызывающему экрану, multipart не получает ошибочный JSON Content-Type, auth не добавляет токен в URL, API client tests покрывают запросы и ошибки.

### Этап 5. iOS поиск и каталог артистов

**Владелец:** junior UI. **Контракт/ревью:** senior.

Нижняя вкладка не добавляется. До реализации координатор фиксирует, нужен ли отдельный полный список артистов или поиск артистов остаётся частью существующего общего поиска. Не добавлять вход из библиотеки без отдельного решения пользователя. В любом варианте обеспечить поиск по артистам; переход из результата общего поиска на страницу артиста обязателен.

**Функции:** список компактных artist items, поиск по имени, empty/loading/error/retry, быстрый переход к ArtistDetail по ID, artwork placeholder, доступные label/roles, клавиатура/VoiceOver, длинные имена, refresh policy.

**Производительность:** API не отдаёт треки для строк каталога; не создавать десятки тысяч тяжёлых image requests; использовать существующий image/cache компоненты и размеры. Раз отсутствие infinite scroll — каталог должен быть конечным списком; согласовать разумный response cap/поиск до запуска реализации.

**Приёмка:** поиск debounce/cancel не показывает устаревший результат, навигация использует стабильный ID, пустой и ошибочный список различимы, тесты каталога покрывают состояния и переход.

### Этап 6. iOS страница артиста

**Владельцы:** junior UI и отдельный junior upload только если файлы ownership непересекаются; senior ведёт интеграцию.

**Композиция:** имя и изображение артиста; действие edit artwork; популярные треки в установленном порядке; дискография с годом и обложкой альбома; элементы ведут в существующий album screen; трек запускается существующим player controller. Не добавлять bio/external links.

**Состояния:** loading, initial failure + retry, artist not found/deleted, no artwork, no tracks, no albums, popularity unavailable/cold start, upload in progress/success/failure, upload invalid type/too large, offline cache policy, long artist/album/track names.

**Плеер:** имя исполнителя становится понятным tappable control с удобной touch target; нажатие передаёт stable artist identity и не меняет текущий трек/очередь. Плеер остаётся доступен при открытом экране согласно существующей архитектуре.

**Поиск:** нажатие на artist result из общего поиска навигирует на ArtistDetail; не должно повторять поиск. При возврате сохраняются query, результаты и scroll offset насколько позволяет текущий navigator/lifecycle.

**Альбом:** имя album artist/artist на странице альбома кликабельно и открывает соответствующую страницу; если у album artist нет стабильного ID/нет найденной записи, поведение должно быть определено: не создавать пустой экран, использовать поиск по имени либо скрывать control. Не менять artist labels в track rows.

**Приёмка:** UI tests на source navigation paths, player remains unchanged, album deep path, back restoration, states; ручной simulator/device smoke test по таргетным размерам и VoiceOver при доступности среды.

### Этап 7. Интеграция и независимое ревью iOS

**Владелец:** координатор + senior reviewer, не автор основного UI.

- Свести backend и клиентские изменения только после backend/API contract acceptance.
- Проверить diff на случайно попавшие файлы и незакоммиченные изменения пользователя.
- Запустить точечные backend и iOS проверки по package scripts и инструкции проекта; затем полный Jest suite и Expo SDK 58 export, если локальные prerequisites доступны.
- Проверить artist ID consistency между search result, player track, album detail и catalog.
- Проверить cancellation/unmount и быстрые переходы между двумя артистами; поздний ответ предыдущего запроса не должен заменить новый экран.
- Проверить image replacement cache busting, unauthorized requests, delete/failure recovery.
- Проверить, что ranking по просмотрам не использует client-provided arbitrary counts и не принимает бесконечные progress events.
- Проверить вручную в симуляторе/устройстве визуальное соответствие ориентиру без утверждения, что это пиксельная копия Apple Music.

**Gate 2:** iOS считается принятой только по реальным diff и командам проверок, не по worker completion status.

### Этап 8. Веб, отложенный следующий этап

Не включать в текущий Run, если владелец отдельно не расширит scope. После iOS gate:

- решить размещение каталога и страниц артиста в существующем web library/search;
- добавить web API types/cache, artist catalog/detail, playlist/player-preserving navigation и artwork editor;
- использовать тот же backend contract и те же semantics популярности/изображения;
- добавить web tests и визуальную проверку в целевом браузере;
- не менять веб заранее только для «симметрии» с iOS.

## 10. Проверки и критерии готовности

### Backend

- `cd brain && source ../venv/bin/activate && pytest -xvs` (или утверждённое эквивалентное venv).
- Миграция проходит на пустой и legacy БД, повторное init не меняет данные повторно.
- Request/query count и размер catalog DTO проверены на 10k+ искусственных записей без аудиофайлов.
- Существующие тесты поиска и альбомов проходят.
- `git diff --check`.

### iOS

- Перед кодом прочитаны versioned Expo SDK 58 docs.
- Сначала точечные Jest suite для новых модулей и затронутых Search/Player/Album/navigation flows.
- Затем полный Jest suite (`npm test -- --runInBand`, если это соответствует актуальному package script).
- Expo export/bundle по текущему package script, если среда и зависимости позволяют.
- UI smoke: каталог → артист → альбом → назад; поиск → артист → назад с тем же запросом/позиции; плеер → артист при непрерывном воспроизведении; загрузка/замена/удаление изображения.
- Симулятор/устройство: нет перекрытия текста/контролов, доступны touch targets, длинные имена, отсутствие обложки, VoiceOver labels.
- `git diff --check`.

### Итоговый продуктовый acceptance

- Артист без имени не появляется.
- Поиск артиста открывает именно страницу, а не выполняет ещё один текстовый поиск.
- Нажатие на исполнителя в player открывает страницу, текущее воспроизведение сохраняется.
- Album artist кликабелен по принятому fallback contract; track-row artists не становятся кликабельными.
- На странице видны вручную задаваемое изображение, популярные треки и дискография.
- Рейтинг следует утверждённой метрике просмотров, сортирован от большего к меньшему и стабилен при равенствах.
- Поиск каталога работает на общем списке; бесконечной прокрутки нет.
- Back navigation сохраняет поисковый контекст.
- Веб не имеет изменений в текущем этапе.
- API не выдаёт пользователю локальные пути к файлам; загрузка ограничена/валидирована и не ломает существующее изображение при ошибке.

## 11. Риски и вопросы для контроля

1. **«Просмотры» не определены.** Счётчик открытий страниц не равен популярности треков. До продуктового решения нельзя реализовывать ranking contract.
2. **Неизвестно, есть ли надёжная playback history.** Проверить event pipeline и смысл события (play request, фактический старт, уникальный track/user/day, прогресс). Не считать каждое `onPlaybackStatusUpdate` просмотром.
3. **Разные написания артистов.** Без alias table каталог может содержать дубль-сущности; точное сравнение текущего поиска именно так работает. Пользователь пока не подтвердил политику.
4. **Нет согласованного top-N.** Полный список популярных треков может быть длинным; бесконечный scroll запрещён, поэтому нужно решить top-N/явную кнопку «Все треки»/обычный конечный список.
5. **10k+ треков не означает 10k артистов**, но полный payload и обложки могут быть тяжёлыми. Возвращать компактный список и измерить его.
6. **Альбом может иметь разных исполнителей трека и альбома.** Membership должен объединить источники без случайного приписывания всего compilation одному исполнителю.
7. **Стабильный ID.** Поиск сейчас отдаёт artist name без гарантированного ID. При ручном artwork и навигации только по строке возникнут rename/case collision и кэш-проблемы; senior должен выбрать identity model.
8. **Хранение изображения.** Нельзя выводить arbitrary file path; нужно определить media endpoint, authorization, cache headers и уборку старого файла.
9. **Пользовательские изменения.** На момент составления документа dirty worktree содержит изменения в iOS player components/tests/scripts и `docs/design/ios.md`. Координатор должен повторно проверить точный status и исключить перезапись этих правок.
10. **Внешняя документация Expo.** Версию Expo SDK и доступные API проверять по versioned docs, не полагаться на память или latest docs.

## 12. Протокол приёмки результатов агентов

Для каждого Dispatch координатор:

1. Проверяет, что ответ относится к актуальному Task/Dispatch и исполнитель имел нужное ownership.
2. Читает diff/артефакт и сверяет фактически изменённые файлы с allowlist.
3. Проверяет команды и реальные результаты, при необходимости повторяет тесты.
4. Проверяет каждый acceptance-критерий независимо; completion outcome не заменяет проверку.
5. Отвечает на все вопросы агента; не оставляет delivery batch непрочитанным.
6. Для failure или unknown outcome сначала исследует state/receipt и применяет предусмотренное восстановление; не создаёт дубликатную попытку только из-за тишины.
7. После settlement принимает решение reuse/retain/release ресурса по установленному Orca workflow.
8. После review findings создаёт отдельный bounded fix Task и повторную проверку.

Финальный отчёт Run перечисляет: принятые решения, выполненные Tasks и исполнителей, изменённые файлы, проверки с pass/fail, review findings и их статус, открытые блокеры, состояние worker resources, а также явное подтверждение, что веб не менялся.

Веб остаётся отдельной будущей задачей, если владелец явно не расширил scope.
