## Verified additional findings

**S01 — P1: a stale request can play after logout, bypassing guarded native APIs.** Lines **748–754, 817–826**. After `play(...,{requestId:'old-request'})` and `cancelCurrent('logout')`, call `setIntent(play, old-request)`: null current request skips the mismatch guard; null current attempt skips guarded play and invokes legacy `player.play()` even with `identityAvailable:true`. VM observes **one unguarded play and native intent=play after cancellation**. This is distinct from the already routed recovery-header identity race. **Correction:** reject supplied IDs unless they equal an active current request; require active ownership/attempt for capable players and never use missing context as permission for unguarded fallback.

**S02 — P1: pause during initial selection headers is overridden by later play.** Lines **1519–1521, 1663–1689, 1855–1856**. Begin public play with deferred headers, call public pause, then resolve headers. Generation/server checks still pass; replace uses explicit null guards and the final play uses null revision without revalidating current pause. VM observes **one additional accepted guarded play, JS intent=pause but native intent=play**. It uses initial installation, not the already routed recovery-header case. **Correction:** capture/recheck request/auth/intent/seek context after asynchronous work and immediately before installation/play; an explicit selection must not retain unlimited play authority after a newer pause.

**S03 — P1: retry treats the same logical selection as a new play, dropping pause/position and replaying the start ledger.** Lines **891–924, 1533–1557, 1063–1065**. Establish progress for one request, user-seek to 42, complete seek, pause, then call `retryCurrent`. VM sees **position reset to 0, zero restore seeks, an additional play**, and after genuine new progress **didStart=true a second time for the same request**. `retryCurrent` forwards into the selection reset path with `isUserSelection:true`. **Correction:** preserve logical selection/start/finish ledger, current intent and latest seek target while creating a fresh attempt/bounded episode; do not reuse full new-selection initialization for technical/manual retry. The paused/position and duplicate-start symptoms share that reset cause.

**S04 — P2: omitted request IDs collapse genuine A/B/A selections into one logical request.** Lines **1353–1356**. Public play A→B→A without explicit IDs yields **one distinct request ID for three selections** because the current request is reused before generating a new one. The contract allows omitted IDs and requires the coordinator to generate them. **Correction:** generate a new logical request for a genuine selection; carry the previous one only through explicitly identified retry/reuse paths.

**S05 — P1: resuming previously confirmed playback creates an unmonitored episode.** Lines **790–803, 301–307, 1063–1077**. Establish sustainable progress, pause, wait, resume, then deliver no further progress. Resume arms startup but retains `_confirmedPlaybackStarted=true`; its timer's condition cannot fire, and pause cleared the stall timer. VM remains **playing at 30,001 ms after resume with zero active timers**, still under startup pressure. **Correction:** initialize attempt/episode progress confirmation afresh for resume, separate it from the logical one-shot history ledger, and arm capability-aware bounded startup/global/stall monitoring. This is a new-resume-state defect, not the known first-selection 30,800-ms overrun.

**S06 — P2: legacy resume arms an unattributed watchdog and reports a false playback error.** Lines **795–803, 297–319**. Initial legacy play correctly skips the startup watchdog, but pause/resume unconditionally arms it. With no capability/attributed events, VM reaches **status=error, kind=timeout at 15,000 ms**, despite no attributable evidence of failure and no replacement. **Correction:** keep attributed startup/stall watchdogs disabled permanently for capability-absent playback on every entry path, while retaining presentation and explicit retry. Zero automatic replacements alone is insufficient fail-closed behavior.

**S07 — P1: a later stall still uses the expired original startup deadline.** Lines **349–385, 1094–1111**. Establish sustainable playback, continue advancing through 41 s, then stop progress. At 51 s VM immediately becomes **error with recoveryCount=0** because `_scheduleAutoRecovery` compares against the old 30-s startup deadline. The separately assigned 81-s stall deadline is unused for that admission and is measured from stall detection instead of last progress. **Correction:** sustainable proof ends startup/recovery episode ownership; later stalls get a fresh bounded episode based on last accepted progress, with a fresh per-episode replacement cap and one consistent deadline. This is explicitly post-sustainable playback, separate from the already reported initial total-budget overrun.

**S08 — P2: successful recovery never releases scheduler pressure after a previously stable episode.** Lines **1089–1111, 395–405, 599–600**. Establish stable playback, trigger recovery, acknowledge a successful restore seek, then supply two new forward progress events spanning >1 s. VM current status is playing but **last scheduler pressure remains recovering**, because `_hasStableProof` stayed true and prevents another stable transition. Current-cache admission is only performed during initial play (**one call in the trace**). **Correction:** scope sustainable proof/pressure transitions to the current resume/recovery episode, and ensure cancelled current-cache ownership can be re-admitted appropriately. The missing stable pressure call is verified; actual scheduler download cancellation/rescheduling is not executed by this mock and still needs integration coverage.

**S09 — P1: source-start server checks do not cover asynchronous installation or recovery epochs.** Lines **1363–1385, 1663–1693, 474–490**. Two VM cases: change the URL provider while initial headers are pending and resolve them—**the old-origin URL is installed**; change provider before recovery—recovery uses the new URL but **serverEpoch stays 0 and scheduler.cancelAll is never called**, leaving incompatible background ownership unrevoked. **Correction:** resolve/recheck effective URL and server/auth epoch at actual source/task boundaries, cancel incompatible work on a detected change, and discard headers/results from an obsolete origin context. The tests expose origin booleans/counters only, not real URLs/credentials; no actual download leakage is claimed.

**S10 — P2: unstructured native text is guessed to be auth/non-retryable.** Lines **64–74, 1136–1144, 1178–1182, 614–629**. After the permitted automatic attempt, a synthetic codec error containing the substring `author` becomes **kind=auth, retryable=false**, with **no numeric HTTP status**. The snapshot classifies arbitrary `auth`/`unauthorized`/`401` text, and similarly guesses not-found from message text. **Correction:** use available numeric structured status only for HTTP/auth semantics; otherwise retain sanitized generic playback failure. The real native error/UI pipeline is not exercised here.

**S11 — P1: the binding `getHeaders` play option is ignored for initial installation.** Lines **1359–1361 versus 1663–1665**. Public `play(...,{getHeaders})` stores the provider but initial acquisition checks only `options.getHeadersAsync`. VM observes **zero provider calls and no supplied source headers**; the binding 4.6 signature uses getHeaders. **Correction:** normalize both supported names/default provider once and invoke that effective provider on each remote source start, preserving bounded cancellation and freshness. This is separate from the known header-duration/total-budget defect.
