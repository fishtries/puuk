## 1. Результат и границы

У трека и альбома есть независимые упорядоченные списки артистов. `TV Girl/George Clanton` можно исправить на два профиля, не меняя аудиофайл. Трек находится у обоих участников. В плеере нажатие на строку с несколькими именами открывает меню выбора, с одним — сразу профиль. Исправление переживает сканирование, чтение редактором, восстановление записи и обновление рекомендаций.

Текущий Run: backend, импорт через бот/сканер/восстановление, iOS, исправление старой библиотеки, разнообразие рекомендаций. Веб-интерфейс — следующий Run; совместимость его чтения и безопасное поведение старых записывающих запросов входят в текущий.

Не входят: роли main/feat., автоматическое изменение названий треков, выделение гостей из title, глобальное объединение вариантов написания/регистра, внешнее обогащение всей библиотеки, новая система идентичности релизов, переписывание всех редакторов тегов, изменение аудиоданных, переименование файлов, перевекторизация музыки.

## 4. Предлагаемая модель данных

### 4.1 Один владелец правил

Ввести один доменный модуль состава артистов (предлагаемые файлы `repositories/artist_credits.py` и `services/artist_credit_service.py`, только если разделение действительно скрывает SQL и сценарии). Он владеет нормализацией, упорядочиванием, источниками, ручным приоритетом, заменой списков и пакетным чтением. Не размножать split/merge/normalize по роутерам и клиентам.

ID артиста сохраняет действующую формулу `art_ + sha256(normalized_name)[:32]`. Уже существующие одиночные артисты сохраняют ID и artwork. Порядок участников не влияет на ID артиста. Не вводить роли, внешние ID как новую identity или aliases имён.

Предлагаемые таблицы и поля; окончательный SQL закрепить на Gate 0:

| Хранилище | Содержание и инварианты |
|---|---|
| `artists` | `id`, `normalized_name UNIQUE`, display name по согласованному действующему правилу. Registry не означает автоматическое присутствие в каталоге. |
| `track_artists` | `track_id`, `artist_id`, `position`; PK `(track_id, artist_id)`, UNIQUE `(track_id, position)`, индексы обратного поиска, FK. |
| `album_artists` | `album_id`, `artist_id`, `position`; аналогичные ограничения. |
| Состояние состава трека | revision, флаг ручного override, снимок последнего импортированного структурированного списка и его источник. Можно компактными колонками в tracks. |
| Состояние состава альбома | Аналогичные поля в albums. Состояния трека и альбома независимы. |
| Журнал массовых операций | ID операции, автор, точный scope, before/after списки и revisions, результат. Не хранить аудиофайлы в журнале. |

Снимок источника и эффективные связи нужны для разных целей: источник может обновиться, но ручной состав остаётся. Не хранить три конкурирующих эффективных списка. JSON допустим для снимка входных данных/журнала, а не вместо индексируемых связей.

Существующие `tracks.artist` / `albums.album_artist` сохранить как legacy/source-значения для совместимости импорта и прежней идентичности релиза. **Ручная правка состава не перезаписывает эти колонки и не меняет существующий album ID.** Публичные строки формируются из эффективных связей. Это разделение должно быть явно названо в коде: старые поля не использовать для каталога, навигации или diversity.

Изменение состава альбома не меняет `(title_normalized, album_artist_normalized)`, по которым старый импорт узнаёт релиз. Тогда старые теги продолжают находить тот же album ID, а ручные участники сохраняются. Новый импорт со структурированным списком также передаёт legacy/source album identity отдельно от display. Автоматическое объединение одинаково названных релизов по новому списку не входит в Run: обнаруженные дубли вынести в отчёт.

Существующий album merge обязан переносить/согласовывать связи и source-состояние транзакционно. При конфликте двух разных ручных списков возвращать конфликт до изменений; не выбирать произвольно один и не объединять списки молча. Переименование альбома и уже существующая смена album identity остаются отдельными сценариями.

### 4.2 Инварианты

- Список упорядочен, повтор одного artist ID удаляется с сохранением первого места. `A` и `a` остаются разными артистами.
- Пустое имя и reserved Various Artists не создают registry-профиль. Пустой список валиден; ручное очищение также защищено override и не восстанавливается из файла автоматически.
- Отсутствующее поле не равно пустому списку: отсутствие входных structured credits не очищает сохранённый состав.
- Замена связей, revision и bump каталога — одна транзакция. Повтор того же списка не создаёт ложных изменений.
- Удаление трека/альбома каскадно удаляет связи; не удаляет общий профиль или чужие связи.
- Каталог включает артиста с живыми track credits либо с album credits у непустого альбома. Последнее — техническое расширение прежнего правила, необходимое для самостоятельного состава альбомов. У такого артиста допустимы `track_count=0` и непустая дискография.
- Артист без живых связей исчезает из каталога. Registry/artwork не удалять автоматически; возможное возвращение того же имени сохраняет identity.
- Участники трека не изменяются от редактирования участников альбома и наоборот.
- Правка состава не меняет track ID, file path, album membership, лайки, историю, плейлисты, позиции, lyrics, cover version, file stat и loudness fingerprint.

## 5. Импорт и приоритет источников

1. Структурированный массив из сопоставленного источника (например, Spotify `song.artists`) проходит до SQLite без join/split. Проверять сопоставление с конкретным файлом; не переносить состав соседнего результата.
2. Читалки форматов возвращают все явно сохранённые значения artist и album artist. Старые строковые поля сохраняются для существующих потребителей.
3. Единственная строка из файла — одно имя, если для неё нет проверенного точного правила. `/`, `,`, `&`, `x` и `feat` не универсальные разделители. Не извлекать состав из title.
4. При ручном override обновлять только source snapshot. Эффективные связи не менять. При отсутствии override можно обновить состав из достоверного structured source; менее информативный legacy fallback не должен схлопнуть уже известный structured list. Явно определить ранги источников и tombstone/empty semantics в тестах.
5. Повторная загрузка через бот, CLI scan, library refresh, recovery из Qdrant, GET редактора, resync и восстановление незавершённой metadata mutation используют одни правила.
6. Альбомные участники берутся из album-level source. Не объединять участников всех треков и не выдавать гостей за авторов релиза. Если album credits неизвестны, не добавлять альбом всем track artists; сохранить непустое legacy album attribution, иначе оставить без атрибуции и показать в отчёте.
7. Для уже существующего track ID сканирование сохраняет текущую связь с альбомом при неизменной source identity; не создаёт копию релиза из-за отличия ручного display от тегов.

Новая функция не записывает participants в теги файлов, включая нормализованную строку через запятую. Бот может сохранять свою существующую обработку скачанного файла; передача structured credits в Puuk не требует нового изменения тегов. Остальные исторические операции редактора файлов не перепроектировать в рамках этой функции.

## 6. API, чтение и совместимость

### 6.1 DTO

Предлагаемый `ArtistCreditDTO`: `{id: string, name: string}`. Position задаётся порядком массива, role отсутствует.

```json
{
  "artist": "TV Girl, George Clanton",
  "artist_id": null,
  "artists": [
    {"id": "<stable TV Girl id>", "name": "TV Girl"},
    {"id": "<stable George Clanton id>", "name": "George Clanton"}
  ],
  "artists_revision": 3
}
```

- Track DTO: `artists` — состав трека. `album_artists` — состав связанного альбома там, где DTO предоставляет album attribution; строка `album_artist` должна соответствовать ему.
- Album DTO: `artists` — состав самого альбома; `artist` и `album_artist` — display строка. Не использовать track credits как fallback.
- Старый `artist_id`: единственный ID только при одном участнике, иначе `null`. Не вычислять ID от объединённой строки и не отправлять старого клиента к случайному первому участнику.
- Для старых DTO без массива новый клиент может построить singleton из валидного старого `artist_id` и имени. Не делить текст на клиенте. Присутствующий `artists: []` не заменяется legacy fallback.
- Списки/детали/поиск/лайки/история/плейлисты/волна/популярные треки используют один контракт. Отдельный DTO редактора также возвращает эффективные DB credits, а не artist из файла.
- Пакетно обогащать списки: один bounded/chunked запрос связей на пачку, не SQL-запрос внутри `serialize_track` для каждого элемента. Учитывать лимиты SQLite bind parameters и `limit=0` текущего каталога.
- Поиск участника находит совместный трек один раз. Счётчики используют DISTINCT; join двух многозначных связей не размножает треки и альбомы.

### 6.2 Изменение состава

Предлагаемые выделенные операции:

- `PUT /api/tracks/{id}/artists`;
- `PUT /api/albums/{id}/artists`.

Тело: `{"artists":[{"id":"existing-id"},{"name":"New Artist"}],"expected_revision":3}`. Каждый элемент содержит ровно id или name; известные id валидируются. Сервер нормализует новое имя и возвращает полное актуальное DTO. Для первого API выбрать конкретные лимиты числа участников/длины имени и записать в контракт, не ставить произвольные ограничения в разных клиентах.

Операция целиком выполняется в SQLite, не требует доступного аудиофайла. `409` — конфликт revision, `422` — недопустимый ввод, `403` — права, `404` — отсутствующая сущность. Права трека сохранить: admin или uploader; альбома — действующее правило проверки доступа к его трекам. Не вводить для обычного редактора новый admin-only запрет.

### 6.3 Старые PATCH-запросы

Веб и старый iOS отправляют строку artist вместе с другими полями, даже когда её не меняли. До файловой операции сравнить её с актуальным display/source и классифицировать запрос:

| Запрос | Предлагаемое поведение |
|---|---|
| artist отсутствует | Состав не меняется. |
| artist совпадает с актуальным display или актуальной source-строкой | Удалить поле из файлового patch; сохранить состав. Другие поля редактируются как раньше. |
| Строка изменена у multi-artist сущности | `409` до любых файловых/DB изменений: требуется структурированный редактор. Нельзя схлопывать массив или угадывать разделители. |
| Изменена только строка у singleton/empty сущности | Адаптировать в замену DB credits одним буквальным именем; без записи тегов. |
| Изменены одновременно legacy artist и другие данные, требующие записи файла | Предлагаемый ограниченный fallback — `409` до побочных эффектов с просьбой редактировать участников отдельно. Не добавлять скрытую частичную транзакцию файл + DB ради старого клиента. |

Это явное ограничение старого редактора, а не полная совместимость записи. На Gate 0 проверить матрицу на реальных payload веба; чтение и редактирование несвязанных полей с неизменной строкой должны работать. Сохранение несвязанных полей новым iOS не отправляет artist/album_artist вообще.

Неизменённые поля, которые клиент присылает «на всякий случай», нужно отфильтровать: artist-only изменение не должно переписывать файл из-за неизменённых title/lyrics/cover_action. При stale display не принимать строку за достоверную ручную замену multi-artist состава.

### 6.4 Дискография и популярность

- Трек принадлежит всем `track_artists`; популярность — существующие play-start события этого track ID. Событие по-прежнему одно на `(user, track, UTC day)`, не по одному на участника.
- При исправлении состава существующие события учитываются у актуальных участников. Не дублировать события и не пересчитывать историю в отдельные artist counters.
- Альбом принадлежит только `album_artists`, если в нём есть треки. Участие B в одном track credit не добавляет album credit B.
- Совместный альбом появляется у каждого своего исполнителя ровно один раз. Число треков альбома — число треков релиза, а не число совпавших credits.
- Нулевые участники/Various: сохранить agreed placeholders; play-start eligibility проверять по эффективному составу, не raw строке.

## 7. Исправление существующей библиотеки и массовые операции

### 7.1 Миграция схемы и безопасное начальное заполнение

Новая миграция после 011 (номер проверить перед началом). Повторный init/backfill идемпотентен. Начальное заполнение сохраняет целую legacy строку как одного артиста, не выполняя эвристическое деление. Existing одиночные IDs сохраняются. Various/пустые исключаются. Backfill альбомов использует album artist, не гостей из треков.

Если для вычисления ID нужен Python, выполнить data migration через явный versioned migration шаг с транзакцией и checkpoint; не оставлять бесконтрольное пересоздание links на каждом startup. Не помещать сетевые вызовы или чтение всей фонотеки в startup migration.

### 7.2 Отчёт и применение

Предлагаемый инструмент `brain/reconcile_artist_credits.py` (имя окончательно закрепляет координатор):

- Режим отчёта по умолчанию, без изменений. JSON для применения, читаемая таблица для просмотра.
- Для каждого предложения: тип сущности, IDs, before list/source, after list, причина/источник, уровень неоднозначности, revision/fingerprint и число затронутых записей.
- Структурированные исходные данные можно использовать как доказательство. Пунктуация даёт кандидата, но не подтверждение.
- Точные правила для трёх форм `TV Girl…George Clanton` отделить от общего parser. Проверить исходные данные перед применением; примеры исследования не являются глобальным allowlist.
- `Chase & Status/Stormzy` не превращать в `Chase`, `Status`, `Stormzy`; `Earth, Wind & Fire`, `AC/DC` и подобные цельные имена не делить.
- Для сомнительного случая оставить исходный список и причину в отчёте. Не считать его молча успешно исправленным.
- Применение только выбранных строк отчёта; перед транзакцией проверить revisions и состав выборки. Устаревший план не применять частично без явного результата.
- Исправленные записи получают защищённый override и durable before/after журнал. Повтор применения того же operation ID возвращает прежний результат без второго изменения.
- Отмена операции восстанавливает только её credits/source override state, если after revision всё ещё совпадает. Более поздние правки не затирать. Полный restore БД не использовать как обычный undo.

Схема уже может работать до очистки: unresolved составной артист временно остаётся видимым. В отчёте выпуска указать число исправленных и оставшихся неоднозначных записей. Не объявлять все фиты исправленными лишь на основании появления таблиц.

### 7.3 Массовая замена в продукте

Admin-only действие со страницы составного артиста: «Исправить артиста в треках». Общий редактор задаёт замещающий список; preview показывает before/after и количество. Album scope выбирается отдельно, не применяется автоматически вместе с треками.

Семантика: заменить одно точное вхождение исходного artist ID на список, оставив остальных участников и их относительный порядок. Например `[X, A&B, C] → [X, A, B, C]`; после нормализации убрать повторы. Не заменять всю строку credits и не выполнять substring replacement.

Предлагаемый API — отдельные preview/apply операции в artists namespace. Preview фиксирует точные IDs и revisions; apply содержит request/operation ID и проверяет актуальность **всей выборки**, включая изменение её membership. Один transaction либо явный conflict, никаких незаметных пропусков. Точный URI/envelope закрепить на Gate 0.

Не копировать artwork составного артиста всем новым участникам. Исходный профиль исчезает только после исчезновения всех его живых связей. Переход назад после массовой замены не должен оставлять пользователя на бесконечной загрузке исчезнувшего профиля.

## 8. iOS

### 8.1 Навигация

- Строка имён всегда отображает участников через запятую.
- 0 доступных профилей — обычный текст; 1 — прямой переход; 2+ — меню с отдельным пунктом каждого артиста в исходном порядке и отменой.
- То же правило для исполнителей альбома. Имена внутри обычных строк треков не превращать в новые navigation controls: прежний scope сохраняется.
- Использовать существующий menu/sheet механизм, доступный в проекте; сначала прочитать `puuk-ui` и platform design guide. Не устанавливать новую библиотеку ради этого меню.
- Открытие/закрытие/выбор не меняют текущий трек, очередь, позицию воспроизведения и контекст возврата. Учесть переход во время смены трека: не открывать профиль из уже устаревшего списка.
- Accessibility: понятное название действия, touch target, фокус, длинные имена/много участников/крупный текст. Menu нужен именно потому, что отдельные мелкие ссылки неудобны.

### 8.2 Редактор

Предлагаемое устройство: в существующих TrackEditScreen/AlbumEditScreen вместо одиночного artist input — список и действие «Изменить артистов», открывающее общий редактор состава с собственным сохранением. Так DB-only операция не смешивается с сохранением обложки/lyrics в файл.

Редактор: поиск существующих, явное добавление нового имени, удаление из текущего состава, кнопки порядка (drag не обязателен), сохранение/отмена. Не создавать registry-артиста при вводе до сохранения. Невалидные/повторные имена показывать понятно, ошибки сохраняют введённый список. При revision conflict загрузить актуальную версию и дать повторить осознанное изменение.

Не затирать несохранённые title/lyrics/cover в родительском редакторе после возврата. Ясно показывать, что состав уже сохранён отдельным действием. Фразу AlbumEditScreen о записи «всех изменений в теги всех треков» уточнить: она больше не должна относиться к артистам.

После сохранения использовать DTO сервера. Сейчас TrackEditScreen собирает событие из локальной строки — это заменить для нового пути. Обновить API cache, текущий трек/очередь/последний сохранённый трек, открытые album/artist/search представления через существующие события и invalidation. Массовая операция инвалидирует весь затронутый scope; не отправлять тысячи отдельных событий без необходимости.

Нижние вкладки не добавлять. Отдельная UI-команда «сбросить к тегам» пока не обязательна; хранение source snapshot оставляет возможность добавить её позже без потери данных.

## 9. Рекомендации и Qdrant

- `_ArtistResolver` возвращает набор artist IDs, не один key; batch lookup из SQLite имеет приоритет над Qdrant для существующей записи.
- Отличать «трек найден с пустым списком» от «трек отсутствует в SQLite». В первом случае не воскрешать артиста из старого payload.
- Для отсутствующей записи — совместимый fallback к structured payload, затем к цельной legacy строке/существующему filename fallback. Ошибку SQLite не маскировать как успешную очистку состава; сохранить ограниченную деградацию и диагностическое сообщение.
- Синхронная правка credits не зависит от доступности Qdrant. Не менять размер/коллекцию векторов, не запускать re-embedding. Structured payload можно добавить аддитивно в очередь новых/восстанавливаемых треков; старые payload продолжают читаться.
- Кандидат расходует лимит каждого своего уникального участника один раз. Если хотя бы один достиг лимита, кандидат пропускается в строгом проходе.
- Сохранить существующее мягкое ослабление лимита при нехватке альтернатив и дедупликацию треков. Учитывать IDs и в fallback, не возвращать одно произведение несколько раз.
- Предлагаемая семантика recent history: взять фиксированное окно последних прослушанных треков, затем собрать всех их участников; не обрезать участников одного трека лимитом имён. Размер окна закрепить в контракте, сравнив прежний `get_recent_artists(limit=5)`.
- Штраф recent artist: при пересечении нескольких участников применять один штраф по максимальной частоте участника, а не сумму по числу участников. Это техническая рекомендация, чтобы большой коллаб не получал произвольный дополнительный штраф. Не менять базовые веса без отдельного измерения.
- Обновить personalized recommendations: artist breadth, caps, recent boost/penalty, tie-break display; `wave_tuning.py` и метрики считают объединение IDs. Не оставить второй путь с одиночным artist.
- Acceptance на фиксированном пуле с A, B, A+B, A+C, D и узким пулом только A: видно соблюдение лимитов и сохранение наполненности при fallback. Субъективное качество оценивается после прослушивания; зелёный тест не доказывает, что подборки стали лучше.

Сначала целевые suites новых модулей и регрессии затронутых путей. Перед интеграционной приёмкой — существующие проверки; каждый backend test использует изоляцию `PUUK_DB_PATH`/`test_db_path`.

### 11.3 Gates

- **G0:** контракт и ownership freeze; продуктовые ответы не потеряны, технические defaults отмечены.
- **G1:** storage + source precedence + повторный импорт зелёные; no-file-write доказан.
- **G2:** API/read/write/bulk/recommendations integrated, legacy matrix проверена.
- **G3:** iOS сценарии и cache invalidation проверены, ошибки не теряют черновики.
- **G4:** независимый review закрыт, отчёт миграции на свежем снимке готов, backup/rollback проверены.
- **G5:** разрешённый выпуск и обработка выбранных data corrections; smoke, учёт unresolved и settled Orca resources.

## 12. Выпуск и восстановление

Текущая задача — подготовка плана; деплой и применение исправлений здесь не выполняются. В реализационном Run сначала закончить проверяемый результат и следовать его разрешённому scope выпуска.

1. Сделать согласованную SQLite backup через backup API/эквивалент, учитывая WAL; копии одного `.db` при работающем writer недостаточно. Сохранить release baseline и отчёт schema/data counts.
2. Проверить upgrade на копии и повторное открытие. Отдельно получить dry-run data report: схема и смысловое разделение старых строк — разные шаги.
3. На коротком окне обновления остановить/приостановить старые writers импорта и heavy worker; сначала обновить совместимые backend + бот + локальный worker. Не оставить старый SFTP writer, обходящий credits rules. Порядок команд сверить с фактическим deploy.sh/runtime, не полагаться на старую заметку о systemd.
4. Через принятый `./deploy.sh` выпустить backend/бот; схема должна быть готова до трафика нового iOS. Обновить локальный worker отдельно. API чтения остаётся совместимым со старым вебом/iOS.
5. Применить выбранные точные исправления из свежего отчёта, проверить revisions, counts, IDs, no-file-write, search/profile/album/ETag. Не выполнять эвристическое массовое деление как побочный эффект startup.
6. Выпустить iOS, smoke: открыть совместный трек → выбрать B → увидеть трек → проверить отсутствие чужого альбома; отредактировать album credits → увидеть совместный релиз у обоих; rescan → повторить проверки.
7. Проверить «Волну» на достаточном и узком пуле, собрать метрики размера выдачи/уникальных участников/срабатывания fallback. В отчёте отделить техническую корректность от субъективной оценки.
8. Для ошибочной data correction использовать условный undo по журналу. При проблеме кода предпочесть совместимый hotfix/roll-forward; простой возврат старых binaries не понимает overrides и не является гарантированным rollback. Для полного восстановления приостановить writers и восстановить согласованный набор schema/code/DB, сохранив более поздние данные отдельно.

## 13. Критерий завершения

Run завершён, когда MA-решения реализованы, все источники используют единые правила, ручной состав переживает повторное сканирование, чужие альбомы не приписываются гостям, меню работает без потери playback state, веб не теряет данные, а рекомендации учитывают всех участников. Исправления старой библиотеки имеют отчёт и точные результаты, сомнительные случаи перечислены отдельно. Обязательные тесты и ручные проверки имеют фактический статус, review findings закрыты или явно приняты, все Dispatches урегулированы.

Итог координатора: что выпущено, какие данные изменены, сколько осталось неоднозначностей, доказательство сохранности файлов/ID, проверки и их пределы, известные ограничения старых клиентов. Не выдавать существование файлов или успешную сборку за продуктовую приёмку.
