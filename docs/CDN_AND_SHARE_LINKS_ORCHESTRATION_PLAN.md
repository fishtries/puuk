# Puuk: защищённая доставка аудио через Yandex CDN и постоянные ссылки

Дата: 2026-11-16. Статус: план для исполнения оркестратором; реализация по этому документу ещё не начата.

## 1. Цель и принятое пользователем решение

Ввести обязательную авторизацию для использования Puuk, постоянные ссылки на сущности каталога для обмена и временные подписанные ссылки для воспроизведения через Yandex Cloud CDN, без привязки к IP.

Итоговый сценарий:

1. Пользователь делится постоянной HTTPS-ссылкой на трек, альбом или артиста.
2. Получатель открывает её в вебе. Без сессии показывается существующий вход/регистрация; после входа восстанавливается исходная цель перехода.
3. Нажатие Play вызывает авторизованный API Puuk. Backend проверяет пользователя, доступность трека и выдаёт короткоживущее разрешение на конкретный файл.
4. Плеер получает аудио через `media.puuk.fun`; CDN проверяет подпись перед выдачей, включая попадание в кеш.
5. При допустимом сетевом отказе клиент ограниченно восстанавливает воспроизведение через существующий авторизованный прямой маршрут.

Принятый компромисс: извлечённая подписанная ссылка является bearer-разрешением — любой её обладатель может использовать её до истечения срока. Это не DRM и не мгновенный отзыв уже выданных прав. Выход из аккаунта не удаляет уже скачанные байты. Не обещать обратного в интерфейсе и документации.

Цель CDN — улучшить доставку аудио за рубежом. Ускорение входа, поиска и рекомендаций в этот результат не входит автоматически. Отдельно измерить задержку API; при её доминировании сформулировать следующую задачу.

## 2. Объём и границы

Обязательно:

- Backend: выпуск CDN-разрешений, защищённый origin-маршрут, совместимый прямой стрим.
- Веб: получение/обновление разрешений, Range, восстановление после ошибок, постоянные ссылки и возврат к цели после входа.
- iOS: CDN в текущем механизме воспроизведения/предзагрузки, обработка истечения и сетевых отказов, генерация тех же постоянных HTTPS-ссылок.
- Каталог: постоянные ссылки на track/album/artist с идентификаторами, а не названиями.
- Эксплуатация: секреты, точные правила CDN, наблюдаемость, постепенное включение, rollback.
- Проверки: реальные отрицательные проверки на прогретом кеше, реальные Range-запросы, веб и iOS, измерения из России и хотя бы одной проблемной европейской сети.

Граница iOS-ссылок: HTTPS-ссылка должна гарантированно работать в вебе и генерироваться iOS. Автоматическое открытие HTTPS-ссылки в установленном приложении требует Associated Domains, AASA, идентификатора команды и подписанной сборки. Проверить наличие возможностей на S0. Если они есть — реализовать; если нет — явно оформить отдельный этап Universal Links, не выдавать `puuk://` за его замену и не блокировать рабочую веб-ссылку.

За пределами первого выпуска: публичное прослушивание, публичные API каталога, SEO/публичные превью закрытых данных, DRM, переезд БД, дублирование backend, HLS-транскодирование библиотеки, новый механизм регистрации, оптимизация рекомендаций. Обложки пока идут существующим путём; их CDN-кеширование — отдельная задача после аудио.

## 3. Проверенные исходные факты и то, что ещё нужно проверить

Факты просмотренного дерева:

- `brain/routers/streaming.py`: `POST /api/media-ticket` принимает `track_id`, возвращает `url`, `expires_in`, `expires_at`; использует `get_current_user`, проверяет запись и файл.
- `GET /api/stream/{track_id}` отдаёт `FileResponse`, доступ проверяется через `get_stream_user` в `brain/auth.py`.
- `app/web/src/api/media.ts`: `resolveAuthorizedAudioUrl` уже принимает абсолютную ссылку из ответа. Кеш тикетов ограничен 200 записями, учитывает authToken и срок действия, запас до истечения — 5 секунд. Есть `invalidateAudioTicket`/`resetAudioTicketCache`.
- `app/web/src/App.tsx`: обязательный auth gate; просмотренная навигация управляется состоянием приложения. Готовый полный контракт share routes не обнаружен; S0 обязан проверить всё дерево.
- iOS: `utils/streamUrl.js`, `utils/playbackCoordinator.js`, `utils/preloadScheduler.js` участвуют в построении/использовании прямых stream URL. Нельзя ограничиться заменой адреса в `shared/api/api.js`.
- iOS `app.json` содержит scheme `puuk`; это само по себе не подтверждает Universal Links.
- На момент проверки `https://media.puuk.fun/` отвечал 200, TLS проходил проверку, был заголовок узла Yandex CDN. `/api/health` отвечает 404; не использовать его как готовый health-check.
- В панели CDN: сертификат выпущен и подключён, HTTPS redirect включён, кеш CDN/браузера выключен, secure token выключен, cookies не игнорируются.

Текущая инфраструктура — контекст, повторно сверить перед изменениями:

| Объект | Значение |
|---|---|
| API/web origin | `https://web.puuk.fun` |
| CDN hostname | `media.puuk.fun` |
| DNS CNAME CDN | `a77ec7546eec5094.topology.gslb.yccdn.ru.` |
| A origin | `128.69.178.203` |
| Сервер по SSH | `192.168.1.117:59348` |

Эти наблюдения не доказывают качество из Европы, кеширование аудио, авторизацию CDN или наличие интеграции в установленном iOS-приложении.

## 4. Правила оркестрации

Этот документ — задание на планирование исполнения, не команда немедленно запускать агентов. При отдельном запуске оркестратор создаёт Run и задачи, следуя актуальному `orca skills get orchestration` и его `references/coordinator-loop.md`.

Роли junior/senior означают ответственность, а не автоматически выбранную модель. В `docs/AGENT_ORCHESTRATION.md` записаны локальные назначения Codex senior и OpenCode junior. Перед dispatch сверить их с текущими инструкциями, доступными launcher/model и явными предпочтениями пользователя; не подменять модель молча. Не копировать устаревшие команды из документа, если текущий CLI требует другой формат.

- Оркестратор S-ORCH владеет контрактом, DAG, интеграционной веткой, журналом решений и итоговой приёмкой.
- Junior выполняет ограниченные задачи по замороженному контракту; не меняет архитектуру и production самостоятельно.
- Senior принимает решения на границах доверия, меняет playback state machine, выполняет production-настройку и рассматривает отчёты junior.
- Независимый senior-reviewer не должен быть единственным автором проверяемого механизма безопасности.
- Junior не порождает собственное дерево агентов. Вопросы отправляет оркестратору через штатный ask/reply.
- Не более трёх одновременно активных workers плюс координатор, если среда не разрешает больше.
- Совпадение write-set запрещает параллельные записи. Разделить этапы либо предоставить Orca-managed child workspaces; один senior выполняет последующую интеграцию.
- Не повторять все проверки чужого отчёта автоматически. Перепроверять критические границы, противоречия и отсутствующие доказательства.

Рабочее дерево уже содержит чужие незакоммиченные изменения: iOS `App.js`, `FullPlayerModal`, `PlayerHeader`, `usePlayerController`, ArtistSelector и тесты; backend рекомендаций; Telegram downloader/source worker; design docs. Перед началом сохранить список и diff/хеши, не делать reset/stash/широкий commit/deploy. Эти изменения не являются частью CDN-задачи. Новый worktree не содержит их автоматически: явно решить, на какой согласованной базе работает каждая задача.

Обязательные инструкции: корневой AGENTS.md, `brain/AGENTS.md`, iOS AGENTS.md. Перед iOS-кодом читать точные Expo SDK 58 docs. Все Python-тесты изолированы `PUUK_DB_PATH`; тесты не запускаются на рабочей БД. Навыки: release-it для стриминга/отказов, a-philosophy-of-software-design для контракта, puux-ux для ссылок/восстановления, puuk-ui только при визуальных изменениях.

## 5. Архитектура, которую senior фиксирует до реализации

### 5.1. Два разных вида ссылок

Предлагаемый контракт постоянных ссылок:

```text
https://web.puuk.fun/track/<track-id>
https://web.puuk.fun/album/<album-id>
https://web.puuk.fun/artist/<artist-id>
```

S1 может скорректировать пути после аудита существующей навигации, но после G1 все клиенты используют один вариант. Идентификаторы берутся из контрактов каждой сущности: не считать album/artist UUID по аналогии с track. Slug названия не идентификатор. Переименование не ломает ссылку; удаление даёт понятное «Недоступно»; для merge определить сохранение старого ID/redirect, если merge уже поддерживается.

Подписанный URL аудио не попадает в Share, адресную строку приложения, navigation state, аналитику и обычные логи. Не записывать auth JWT в query. Подпись CDN — отдельный механизм и отдельный ключ.

### 5.2. Backend-контракт воспроизведения

Сохранить `/api/media-ticket` и совместимые поля ответа. Предлагаемое расширение запроса: необязательная capability доставки (`direct`/`cdn`) для управляемого включения новых клиентов. Отсутствие capability сохраняет поведение старых клиентов. Точные имена закрепляет S1. Не включать CDN всем старым клиентам только потому, что новый сервер умеет подписывать URL.

Новый клиент запрашивает CDN, backend выбирает разрешённую доставку с учётом флага/пилотной группы. Для fallback клиент может запросить direct, но проходит ту же авторизацию и проверки трека. Ответы с разрешениями — `Cache-Control: no-store`.

Один модуль backend скрывает URL, алгоритм провайдера, expiry и выбор direct/CDN. Клиенты не знают signing secret и не реализуют алгоритм подписи.

TTL: стартовое предложение 30 минут, настраиваемое через config. Это не обещание беспрерывности для произвольно длинной паузы или длинного файла. До G1 определить запас до expiry, политику длинных записей и восстановление после sleep. Учитывать часы сервера и клиентский clock skew. Не заменять играющий source таймером без необходимости — это может вызвать слышимый разрыв.

### 5.3. Origin и кеш

Выделенный маршрут, например `/cdn/audio/<track-id>/<content-version>` (окончательное имя в G1), отдаёт только аудиофайл по проверенному ID и версии. Никаких пользовательских путей файловой системы, произвольных URL или обхода `MUSIC_DIR`.

На origin проверяется отдельный секретный HTTP-заголовок, который CDN устанавливает при запросе к источнику. Значение клиентского одноимённого заголовка должно перезаписываться. Проверка constant-time, пустая/неполная конфигурация закрывает маршрут. Секрет не совпадает с JWT_SECRET или CDN signing secret. Отдельно проверить, что origin-аутентификация не обходится заголовками Host/X-Forwarded-*.

На CDN подпись проверяется ДО выдачи кеша. Два валидных разрешения разных пользователей должны попадать в один кеш одинаковых байтов, но отсутствие/подмена подписи после прогрева обязаны давать отказ. Исключение signature/expiry из cache key допустимо только после доказательства такой проверки. Остальные query-параметры отклонять или явно включать по контракту; не допустить подмену версии и контента через query.

Content version — стабильная версия реальных байтов. S1 выбирает источник версии после проверки импортов/редактирования тегов: нельзя вычислять хеш всей библиотеки при каждом Play. Если используется size/mtime, документировать ограничения и обеспечить смену версии при каждой операции изменения файла. Кеширование только по track ID без стратегии обновления запрещено.

CDN-домен разрешает только согласованный media prefix и служебный CORS preflight. Не оставлять через него произвольные auth/admin/API/web routes. Одной UI-галочки кеша на всём ресурсе недостаточно. Выбрать точные location rules либо отдельный origin virtual host; проверить реальную доступность нужных механизмов в Yandex. `Host: web.puuk.fun` сам по себе не является проверкой CDN.

Оригинальные аудиофайлы не изменять; нормализация громкости остаётся в существующем playback пути. Если обнаружится серверная вариативность аудиобайтов, вариант обязан входить в cache key либо такой ответ исключается из кеша.

### 5.4. Удаление, отзыв и секреты

- Перестать выдавать новые разрешения на удалённый/недоступный трек.
- Уже прогретый файл может оставаться доступен по действующему разрешению. Зафиксировать TTL кеша и процесс purge при удалении/замене, включая все версии и сегменты.
- Purge должен иметь ограниченные retries, явный результат и наблюдаемую ошибку; не объявлять удаление из CDN завершённым при timeout.
- Не превращать каждый Play в вызов control-plane API CDN.
- Выход/смена аккаунта очищает клиентский кеш разрешений и отменяет незавершённые операции; отдельный трек, уже скачанный клиентом, нельзя «отозвать» удалением URL.
- Ротация signing secret и origin secret — разные операции. Продумать переходный период поддерживаемыми средствами; если overlap недоступен, считать старые URL недействительными и обновлять их ограниченно.
- Ключи хранятся в серверном env/секретном хранилище и CDN-конфигурации; не в git, Expo EXPO_PUBLIC, веб-bundle, worker prompt, screenshot отчётах или артефактах CI.

### 5.5. Веб, CORS и Range

- CDN URL используется непосредственно медиадвижком, без полной blob-загрузки трека.
- Проверить `crossOrigin` и Web Audio граф нормализации: успешный `<audio>` сам по себе не доказывает работу громкости/анализа.
- Разрешённый web origin — точный origin Puuk; локальные origins только в dev-профиле. Не использовать отражение произвольного Origin.
- Проверить GET/HEAD/OPTIONS, `Range`, `Accept-Ranges`, `Content-Range`, `Content-Length`, ETag, корректные 200/206/416 и выдачу байтов.
- CORS-заголовки должны присутствовать и на значимых ошибках. Preflight не выдаёт аудио и не требует клиентский bearer; реальные GET/HEAD проверяют доступ.
- Не пересылать пользовательский JWT на медиадомен. Подписанный запрос получает доступ собственной подписью.
- Клиентский кеш и edge cache имеют разные правила: не навешивать без разбора `public, max-age` на защищённые ответы браузеру. S1 фиксирует браузерную политику с учётом logout/offline, а edge TTL настраивается отдельно.

### 5.6. Ограниченное восстановление

Один владелец восстановления на платформу, а не независимые retry в API, store, coordinator и плеере одновременно.

Предложение для G1: одна попытка обновить разрешение, затем не более одного перехода на direct при транспортной/временной CDN-ошибке; следующий отказ — видимая ошибка. Зафиксировать общий timeout-бюджет. Веб часто не раскрывает HTTP-код media error — классифицировать по доступным сигналам и результату авторизованного ticket API, не выдумывать код.

401 ticket API → существующий сценарий входа. Отсутствие доступа/удаление → конечная ошибка, не обход через direct. Истёкшая CDN-подпись → запрос нового разрешения после проверки сессии. TLS/DNS/5xx → ограниченный fallback. Не использовать HTTP или отключение проверки сертификата.

Сохранять track, позицию, очередь, play/pause intent и громкость. Поздний ответ на трек A не заменяет уже выбранный B; cancellation/generation token распространяется на refresh и fallback. Нельзя повторно отправлять событие полного прослушивания из-за замены источника.

### 5.7. Постоянные ссылки и вход

- Share возвращает стабильный URL сущности без токенов, имён файлов и секретов.
- Без сессии сохраняется только валидированная цель `{type,id}`; после входа загружается сущность через обычный защищённый API.
- Произвольный `returnTo=https://...` не допускается: только собственные allowlisted маршруты, без open redirect.
- Ссылка открывает сущность, но не запускает звук автоматически и не разрушает текущую очередь.
- Поддержать refresh страницы, browser back/forward, отмену входа, повторное открытие, неизвестный ID, недоступную сущность и ошибки сети.
- Серверный SPA fallback обслуживает известные share routes, но не превращает неизвестный `/api/*` или `/cdn/*` в HTML 200.
- Существующие пути регистрации через Telegram остаются прежними; pending destination переживает фактический сценарий входа, проверенный S0.

S3/J4 и S4/J5 затрагивают общие composition roots: junior сначала пишет изолированный модуль и тесты, senior платформы последовательно интегрирует его в App/store/hooks. Никаких параллельных правок App.js/App.tsx. При ограничении слотов сначала S2+J3+S3, затем S4+J4+J5; это расписание ресурсов, а не изменение зависимостей.

### S0 — база и полномочия

Прочитать инструкции, снять git status/diff, проверить актуальный deploy script и реальные systemd/nginx на сервере. Старый docs/DEPLOYMENT.md может расходиться с production. Составить список существующих проверок и безопасного тестового трека. Никаких массовых скачиваний и тестов на рабочей БД.

Результат: `docs/cdn/S0_BASELINE.md` с ревизией, изменёнными файлами, каталогом тестов, платформенными ограничениями и фактическим playback entrypoint. Не включать секреты.

### J1 — провайдер и инфраструктура

Read-only. Проверить secure-token алгоритм на текущей официальной документации, точную canonicalization URI, scope подписи на один объект, expiry, cache key, сегментацию, purge, CORS, origin header и SNI. Проверить текущие значения в панели без раскрытия ключей. Для неизвестного записать «не подтверждено», а не предположение.

Результат: `docs/cdn/J1_PROVIDER_AUDIT.md`, таблица «требование → поддержка → источник/эксперимент → ограничение». Изучить возможность ограничить routes медиадомена. Отдельно проверить query `mt`/`token`/`expires`: названия и алгоритмы Puuk/Yandex могут различаться.

### J2 — карта кода

Read-only исходников. Перечислить все способы запуска: обычный трек, очередь, волна, повтор, seek, preload, локальный download/offline. Найти загрузку токенов, logout cleanup, cache limits, смену backend URL, share UI и импорт/замену аудиофайлов.

Результат: `docs/cdn/J2_CODE_MAP.md` с файлами и функциями, отдельным описанием старых iOS-клиентов и отсутствующих share screens. Не называть поддержку CDN готовой только из-за абсолютного URL в одном helper.

### S1 — контракт

Создать `docs/cdn/CONTRACT.md`, закрыв все решения раздела 5. Точно определить DTO, feature flags, ошибки, версии файлов, scopes, маршруты, timeout/retry budget, CORS, TTL, отзыв/удаление, iOS fallback и share navigation. Отдельно указать, что подтверждено live probe, а что требует G2/G3.

В G1 ни один пункт границы безопасности не должен оставаться неявным. Если провайдер не поддерживает требуемый per-file scope или проверку перед кешем, исправить проектирование до выдачи реализации junior.

### S2 — backend

Write-set: `brain/routers/streaming.py`, новый содержательный delivery service, `brain/config.py`, минимальные auth/router изменения и целевые тесты. Разрешить миграцию только при доказанной необходимости версии файла, с идемпотентностью и отдельным тестом.

Сохранить legacy endpoint; добавить закрытый origin и выпуск CDN-разрешений; проверить существование/доступность файла, no-store, secrets validation, redaction, deletion/purge hook. Не рефакторить рекомендации/Qdrant и не менять звук. Сетевые control-plane операции вынести из playback request; определить пределы их retry.

Доказательства: unit/integration тесты, disabled-mode совместимость, сравнение байтов, отсутствие секретов в diff/log, отсутствие изменений рабочей БД.

### J3 — независимые проверки backend

Write-set: отдельные новые `brain/test_cdn_*.py`, тестовые fixtures. Первым импортировать `test_db_path`, явно проверить временный путь БД. Тесты исходят из контрактов, не копируют signing implementation как свой oracle. Использовать независимые эталоны провайдера и затем живой smoke S5.

Покрыть подпись пути/expiry, невалидные ID/версии, auth, origin-secret, прямой маршрут, feature flags и purge failure. Не исправлять production-код без передачи дефекта S2.

### S3 — веб playback

Write-set: `app/web/src/api/media.ts`, согласованные части store/engine и их тесты. Окончательный список — J2. Ввести capability, обновление разрешений, дедупликацию запросов на один track/session, cancellation, bounded cache, правильный crossOrigin/Web Audio и однократный fallback. Auth logout должен отменять pending operations и очищать разрешения.

Проверить play/pause/seek/repeat/next, длительную паузу, смену аккаунта, гонку A→B, серверный флаг off. Не пересылать JWT в CDN-запрос и не скачивать полный трек ради старта. Интеграция J4 выполняется этим senior последовательно.

### S4 — iOS playback

Write-set после J2: `utils/streamUrl.js`, `utils/playbackCoordinator.js`, `utils/preloadScheduler.js`, согласованный API-модуль и тесты. Общие hooks/App с чужими изменениями интегрирует senior отдельно после проверки diff.

До изменений прочитать SDK 58 docs и установленный source используемых API. Существующий sync getStreamUrl нельзя молча заменить Promise: изменить границу coordinator/scheduler, определить отмену и приоритет текущего трека над предзагрузкой. Не добавлять второй независимый контроллер воспроизведения.

Локальные download/cache keys опираются на track/version, а не на изменяющийся signed URL. Сохранить logout/offline политику, защиту от чужой сессии, фоновые состояния и блокировку экрана. Проверить, не пересылает ли native player старые bearer headers на новый origin/redirect. Подписанная ссылка не хранится как постоянный `stream_url` каталога.

Доказательства: Jest + фактическая сборка, затем устройство. Моки не заменяют background/seek тест на iOS. Если сборка/устройство недоступны, статус этой части «не проверено», не «готово».

### J4/J5 — постоянные ссылки

По G1 реализовать formatter/parser, безопасную pending destination, share action и tests. Проверить существующие ID форматы и URL encoding. Веб: прямое открытие и refresh, вход, back/forward; iOS: исходящие HTTPS-ссылки, а входящие — по согласованной capability. Поведение unknown/deleted не должно подменяться случайным первым треком.

Junior не добавляет router framework, не переделывает auth и не меняет дизайн всей библиотеки. При отсутствии экрана track детали минимального представления определяет senior. Запись принятого UX в общих design docs — один назначенный интегратор, с сохранением чужих правок.

### S5 — CDN и origin

Снять безопасный экспорт конфигурации и подготовить обратимые точечные изменения. При работе с Zen использовать доступный Hyprland instance из `hyprctl instances`, не фиксировать устаревшую signature из shell env. Секреты не печатать в терминал или отчёт; использовать штатные секретные поля/защищённый ввод.

Настроить HTTPS/SNI/Host, origin header, prefix restrictions, secure token без IP, CORS, cache key, versioned cache, отсутствие кеша auth/error ответов. Эксперимент сегментации проводится на нескольких файлах, не на всей библиотеке. Сохранить DNS validation CNAME. `web.puuk.fun` не направлять в CDN, если он остаётся его источником.

Сначала проверка доступа с выключенным кешем и без массовой выдачи URL. Затем включить кеш только media-prefix, прогреть ограниченный тестовый файл и выполнить всю отрицательную матрицу. До успеха не включать pilot пользователям.

### J6/S6 — QA и независимый review

J6 собирает таблицу сценариев и воспроизводимые ошибки на конкретной ревизии. S6 независимо проверяет границы доверия и минимум повторяет: warm-cache unauthorized, path substitution, origin bypass, JWT leakage и rollback. Отчёт с красным критическим пунктом не принимается по формулировке «в основном работает».

### S7/J7/S8 — выпуск

S7 готовит точный reviewed manifest вместо широкого rsync грязного дерева. Учитывает, что `deploy.sh` может перезапустить и Telegram-бот. Применяет совместимый backend с флагом off, затем CDN config, затем новые клиенты, затем pilot.

J7 проверяет из реальных сетей РФ/Европы и на устройстве, фиксирует фактический app build/version. S8 сверяет критерии, ограничения и оставшиеся задачи. Успех отдельных задач не равен завершению Run, пока обязательные критерии не выполнены.

## 7. Контрольные точки

| Gate | Кто принимает | Обязательные условия |
|---|---|---|
| G0 | S-ORCH | База и чужие изменения учтены; роли и write-set назначены |
| G1 | S1 + reviewer | Контракт заморожен; security scope/cache/expiry/fallback решены |
| G2 | S-ORCH | Backend и независимые тесты прошли; config off совместим |
| G3 | S6 | Live cache security, веб и iOS интеграция, rollback доказаны |
| G4 | S8 | Выпуск проверен на конкретных сборках; географические результаты и ограничения записаны |

Это технические gates между задачами, не автоматические запросы разрешения пользователю. Оркестратор продолжает в уже авторизованном объёме. Только новая покупка/расширение услуг или действительно отсутствующие обязательные сведения требуют отдельного согласования. Не включать платные дополнительные логи/shielding/IP без оценки необходимости и действующего разрешения.

## 8. Минимальная матрица приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Нет сессии → media-ticket | Отказ; нет CDN/direct URL |
| Валидная сессия, отсутствующий файл | Понятная ошибка; не подписывать несуществующее |
| CDN без подписи до/после прогрева | Отказ в обоих случаях |
| Поддельная/истёкшая подпись после прогрева | Отказ, включая Range и HEAD |
| Подпись трека A для трека B/другой версии | Отказ |
| Два валидных разрешения на одни байты | Общий кеш, без обхода авторизации |
| Origin без/с неверным секретом | Отказ независимо от Host/query |
| Origin с правильным секретом | Только согласованный файл/версия; точные байты |
| CDN → auth/admin/произвольный API | Не публикуется через медиаресурс |
| Range начало/середина/конец/suffix | Корректные 206, заголовки и байты |
| Невыполнимый Range | Корректный 416; не HTML и не чужой кеш |
| HEAD/OPTIONS | Корректные заголовки; нет аудиотела/обхода доступа |
| Browser + Web Audio | Звук, нормализация, seek; CORS не блокирует граф |
| Пауза дольше TTL → resume | Ограниченное обновление, сохранённая позиция |
| Быстро A→B, поздний refresh A | B остаётся текущим |
| CDN timeout/5xx | Не более оговорённого числа попыток, авторизованный fallback |
| Ticket API 401/запрет | Нет бесконечного retry и обхода через fallback |
| Logout во время ticket request | Поздний ответ не восстанавливает разрешение/воспроизведение |
| Wi-Fi ↔ мобильная сеть | Нет искусственной IP-блокировки |
| Старый iOS + новый backend | Прямое воспроизведение работает |
| Новый клиент + флаг off/старый backend | Совместимое прямое воспроизведение по контракту |
| Импорт/замена байтов/удаление | Смена версии и purge по выбранной политике |
| Share track/album/artist | Постоянная ссылка без секретов; вход возвращает к цели |
| Подмена returnTo/неизвестный ID | Нет внешнего redirect, понятное состояние |
| App cold/warm link, если Universal Links включены | Одна навигация после готовности auth; без autoplay |
| Логи/аналитика/артефакты | Нет JWT, origin secret или полной подписанной ссылки |
| Rollback | Новые разрешения direct, старые клиенты продолжают работать |

Проверка TTL не должна ждать 30 минут: тестовый TTL короткий, изолированная конфигурация; перед пилотом вернуть согласованное значение. Запросы с неверными подписями не кешировать как долгоживущий 403 для последующих валидных запросов.

## 9. Измерения и эксплуатация

Снять baseline direct и CDN cold/warm для одинаковых треков/битрейта. Включить короткий трек, длинную запись, файл с необычным размером, seek в конец. Замерять DNS/TLS/TTFB отдельно от времени до слышимого старта, задержку ticket API, rebuffer, throughput, refresh/fallback count, origin traffic и cache hit.

Для РФ и Европы записать дату, страну, ASN/тип подключения без персональных IP, версию приложения, узел CDN, sample count. Минимум несколько повторений в одинаковых условиях; не выводить надёжный p95 из двух запросов. Если точек мало, показать сырые результаты/медиану и назвать выборку пилотной.

Предлагаемый критерий пилота: в проблемной европейской сети тёплый CDN снижает медиану времени старта хотя бы на 30% при отсутствии увеличения прерываний; в российской сети нет заметной регрессии (предлагаемый предел 20%). S1 фиксирует окончательные пороги после baseline, до переключения. Не менять пороги задним числом ради зелёного отчёта.

Если CDN ускоряет аудио, но ticket API остаётся узким местом — честно отделить эти результаты. Если cache HIT не подтверждён заголовками/метриками и уменьшением обращений origin, не считать CDN-кеш работающим по одному HTTP 200.

Наблюдаемость: короткий correlation ID, track ID, delivery mode, результат и latency; без query подписи и токенов. Бюджет трафика и alerts — на доступных средствах, не обещать жёсткий spending cap там, где провайдер даёт только уведомления. Не прогревать всю библиотеку во всех PoP.

## 10. Порядок включения и rollback

1. Зафиксировать baseline, конфигурацию nginx/CDN без секретов, текущий рабочий build и точный rollback manifest.
2. Развернуть совместимый backend; CDN выдача выключена, legacy direct проходит smoke.
3. Создать закрытый origin, настроить ключи и подписывание на CDN; не публиковать незащищённый origin ни на промежуточном этапе.
4. Выполнить закрытые probes с кешем off, затем warm-cache security probes на согласованном media-prefix.
5. Выпустить веб и iOS с capability и fallback. Проверить точные deployed assets / app build, а не только исходники.
6. Включить CDN для тестового аккаунта/малой группы; установить период наблюдения, например сутки. Длительность входит в критерии, отсутствие жалоб не заменяет наблюдение.
7. При успехе расширить охват. Постоянные ссылки можно выпускать отдельным обратимым этапом после их UX-проверок.

Стоп-условия: любой доступ без подписи на тёплом кеше, утечка секрета, нарушение origin auth, повреждённые Range-байты, рост ошибок/петель retry, сильная регрессия РФ, непредвиденное потребление.

Rollback доставки: выключить выдачу новых CDN-разрешений → клиенты получают direct, очистить/инвалидировать локальные ticket caches предусмотренным механизмом. Обычный rollback не обязан резко отключать уже играющие валидные CDN URL; оставить их до истечения, если нет security-инцидента. При инциденте отдельно закрыть media resource/сменить ключ и принять необходимость повторного получения URL. Не удалять DNS и сертификат как первый шаг.

Rollback кода — точечные версии reviewed manifest. Не откатывать чужие изменения, не восстанавливать старую рабочую БД поверх новых пользовательских данных. При миграциях заранее доказать совместимость старого backend с новой схемой.

## 11. Формат постановки worker-задачи

Каждый dispatch получает полный текст, а не ссылку «сделай как обсуждали»:

```text
Task: <ID и название>
Role: <junior/senior, launcher/model согласно фактически разрешённой конфигурации>
Objective: <наблюдаемый результат>
Baseline: <commit + согласованные локальные изменения>
Inputs: этот план, CONTRACT.md revision, отчёты зависимостей
Read first: применимые AGENTS.md/skills/versioned docs
Write allowlist: <точные файлы/каталоги>
Forbidden: чужие изменения, секреты в отчёте, production вне назначенной задачи
Contract: <DTO/ошибки/состояния, которые нельзя менять самостоятельно>
Acceptance: <список проверок с ожидаемым результатом>
Evidence: команды, exit codes, число тестов, ревизия/build, redacted artifacts
Escalation: если контракт недостаточен — ask координатору; не угадывать security semantics
Completion: worker_done с outcome и ограничениями, не объявлять partial полным успехом
```

Отчёт worker: изменённые файлы, что изменилось, точные проверки/результаты, оставшиеся ограничения, зависимости для следующего этапа. Для failed tests указать, является ли это дефектом новой работы или доказанным baseline failure. «No tests found» и выход 0 не доказательство прохождения.

## 12. Артефакты и итоговая готовность

Ожидаемые артефакты исполнения:

- `docs/cdn/S0_BASELINE.md`, `J1_PROVIDER_AUDIT.md`, `J2_CODE_MAP.md`.
- `docs/cdn/CONTRACT.md`, `DECISIONS.md` — один владелец изменений контракта.
- `docs/cdn/CDN_RUNBOOK.md` — настройка, секреты без значений, ротация, purge, rollback.
- `docs/cdn/ACCEPTANCE.md` — матрица и ссылки на доказательства.
- `docs/cdn/RELEASE_REPORT.md` — production manifest, web/iOS build, географические результаты.
- Тестовые артефакты хранятся отдельно, без live tokens, персональных данных и полных URL доступа.

Работа завершена только когда авторизованные поддерживаемые клиенты реально получают аудио через защищённый CDN, постоянные ссылки работают через вход, fallback/rollback проверены и результаты РФ/Европа задокументированы. Если iOS ещё не установлен/не проверен либо нет европейской проверки, явно оставить соответствующий этап незавершённым. HTTP 200 на корне CDN не является завершением этой задачи.
