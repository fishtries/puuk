## Findings requiring revision

### G1-01 — High: the actual HTTP/startup scanner cannot implement the promised track identity within S2's allowlist

**Contract:** §3 mutation table, §7.2 lines 230–232, §11 S2 ownership; D02/D07. **Evidence:** `brain/services/library_service.py:24` generates a pathname UUIDv5, then independently uses that ID for album resolution, lookup, insertion and metadata update through line 51. The startup disk reconciliation repeats UUIDv5 generation at line 127. `brain/routers/library.py:7` binds `/api/library/scan` to this service; `brain/api.py:117` uses it at startup. S2 permits `brain/scan.py` but omits `brain/services/library_service.py`.

The contract requires a fresh UUIDv4 after tombstoned same-path reimport and lookup of existing path identity before deriving a candidate. Changing only `repositories/tracks.py:add_or_update_track` cannot silently substitute an ID: this function currently returns no canonical identity, while the scanner continues subsequent writes under its original local ID (`tracks.py:228`–282). Rejecting the old ID prevents resurrection but also prevents the promised legitimate reimport. This is an active entrypoint, not a hypothetical future writer.

**Required fix:** name one canonical ingest/identity operation, its returned ID, and every caller that must consume that ID before album/metadata/Qdrant publication. Add the exact library-service path to a coordinator-reviewed S2 allowance, or narrow the supported move/reimport behavior explicitly while still preventing tombstone resurrection. Cover HTTP scan, startup disk sync, CLI scan, Qdrant restore and repeated same-path reimport in isolated tests. Include the optional loudness recovery creator (`services/loudness_sync_service.py:194`) in the tombstone audit; its normal periodic path uses `create_missing=False`, so do not expand that file's scope without necessity. Preserve every baseline file outside the subsequently assigned integration.

### G1-02 — High: protected-origin CORS and error policy conflict with the existing middleware boundary

**Contract:** §2.1 no-store errors, §4.1 secret enforcement, §4.3 lines 143–149, §11 limits `brain/api.py` to router/lifecycle changes; D09/D14. **Evidence:** `brain/api.py:178` installs application-wide `CORSMiddleware` with credentials enabled, no HEAD in the permitted methods, no If-Range in allowed headers, and the default preflight age. This wraps newly included routers too. Starlette's middleware answers a browser preflight before invoking routing/dependencies, and adds credential/CORS response headers to simple responses. The [upstream implementation](https://raw.githubusercontent.com/encode/starlette/master/starlette/middleware/cors.py) confirms this control flow; the local default Python interpreter has no installed Starlette, so this is source analysis rather than a runtime test of the deployed version.

A secret dependency and OPTIONS handler on the new route alone therefore cannot deliver the specified secret-checked 204 or suppress `Access-Control-Allow-Credentials`; forged-secret preflight can be answered first. HEAD/If-Range preflights fail under the old policy. Likewise, no-store on a successful handler does not cover authentication/validation failures raised before that handler. This does **not** imply that OPTIONS exposes audio, but it contradicts the security/HTTP contract and creates a predictable integration failure.

**Required fix:** freeze the path-specific ASGI/middleware composition for `/cdn/audio/`, direct audio and ticket errors, including ordering relative to account API CORS and exception handling. Explicitly grant the minimal composition/middleware change required in `api.py` and name the implementation owner; avoid changing unrelated account API behavior. J3 must test the assembled app, not an isolated router: missing/wrong/duplicate secret OPTIONS, allowed/disallowed Origin, HEAD/If-Range, 401/422/404/416/500 no-store, and absence of credentials headers on protected media. Keep the live edge-generated error/header gate in addition to these local tests.

### G1-03 — High: new global artist rename is speculative product scope and its compatibility cost is not contained

**Contract:** §7.2 lines 236–238, §11 S2, D02/D03 and DECISIONS “Source corrections and scope implications.” **Evidence:** `brain/routers/artists.py` has artwork and membership preview/apply/undo routes, with no global name-rename endpoint. `artist_credits.py:86` derives identity from normalized names; `_register`/`_set_links` do the same at lines 118/135. Bulk operation snapshots retain names, IDs, revisions and manual-name JSON (`artist_credit_bulk_service.py:221`–238). The dirty, explicitly excluded `services/recommendation_service.py:87`–97 also derives fallback artist keys from names.

The original plan requires stable links under supported rename/merge operations; it does not require inventing a new global artist editor. Current credit replacements are membership edits, which the draft correctly says must not redirect to a guessed first replacement. Keeping the old registered artist as an empty profile already preserves the old artist link under those existing operations. The new PATCH plus permanent name aliases adds a second identity interpretation across ingest, selectors, bulk snapshots/undo and recommendation fallback. Calling the endpoint “small” does not account for these boundaries. In particular, the draft does not settle rename versus outstanding preview/undo snapshots or the name-derived degraded recommendation keys, while prohibiting edits to the latter dirty module.

**Required fix:** preferred v1 scope is to remove the new global artist rename API/name-alias migration and retain immutable existing artist IDs, empty profiles and membership semantics; explicitly document that global artist identity rename is not currently a supported operation. Keep mandatory existing track metadata/album rename stability and album merge aliases. If the coordinator deliberately retains global rename, give it a separately scoped design/owner with concrete snapshot/revision/undo and recommendation fallback semantics and precise preservation/integration allowances before accepting G1. Do not make a pure deterministic name-hash helper perform hidden database access to conceal this dependency. This review rejects the added rename scope as currently proposed; it does not reject stable artist links.

### G1-04 — High: iOS cache admission leaves an unresolved verification branch and a direct-download version race

**Contract:** §6 lines 202–210, especially line 208; §2 direct URLs; D18. **Evidence:** installed SDK58 `expo-file-system/src/NetworkTasks.ts:289` returns `Promise<File | null>` from `DownloadTask.downloadAsync()`, not HTTP status/response headers. The installed native `ios/FileSystemDownloadTask.swift:394` checks status then resolves a file URI. `FileHandle.readBytes` exists, but the draft does not choose an incremental SHA-256 verifier; no such dependency is declared in the app's package.json. S4 cannot add dependencies/native patches under its current allowance.

The text says to hash if supported and otherwise check a server strong ETag/version plus exact length. It does not specify how the chosen downloader obtains that response validator or how a direct download is bound to it. A direct ticket is `/api/stream/<id>?mt=...`, unversioned: after descriptor/hash A is issued, a managed atomic edit can install equal-length bytes B before the download GET. A separate HEAD, authenticated descriptor and size check alone can admit B under cache key A. Local SHA-256 would detect this; an explicit version-bound conditional GET could also prevent it. Neither concrete path is frozen. CDN's immutable path removes this particular race, but direct is a mandatory disabled/fallback path and also feeds the cache.

**Required fix:** choose one implementable SDK58 admission strategy now, including exact allowed dependency/module/API and bounded memory/verification time. Either verify the downloaded bytes against the descriptor SHA-256, or specify a response-aware/version-bound transfer with the required direct HTTP validator/precondition behavior and owner. If the platform cannot establish identity, stream the object and decline persistent admission rather than label it verified. Resolve legacy-cache quarantine under that same strategy. Add equal-length replace-between-ticket-and-GET, partial download, logout/server switch during verification and restart tests. An independent HEAD check by itself is insufficient.

### G1-05 — Medium: optional CDN purge failure is coupled to unrelated direct-only catalog mutations

**Contract:** §3 replacement/delete rules, §9 lines 274–282, disabled defaults in §2.2; D12/D13. The draft requires retirement/purge reservation before managed replacement/deletion and rejects mutations at outbox capacity, but does not condition that reservation on whether any relevant CDN permission was ever issued. Both issuance and purge consumer default off. Consequently a deployment that has never enabled CDN can accumulate mandatory purge bookkeeping and eventually reject ordinary metadata edits/deletes because an optional disabled delivery dependency has no consumer. After rollback the same coupling remains unless explicitly designed otherwise.

Purge is explicitly best-effort, and copied capabilities already have a bounded lifetime. The design needs durable intent for actually exposed versions, not a purge job for every file the application has ever seen. The new coupling is avoidable complexity and an availability regression beyond the original playback task.

**Required fix:** define the ledger predicate for “may have been exposed,” enqueue/coalesce only the required intents, and state behavior before first issuance, during ordinary flag-off rollback and after all relevant expiry/cache-retention windows. Retain tombstones/version correctness independently. Any capacity-based mutation rejection must be limited to mutations that truly require retaining an unresolved exposure intent. Test a never-enabled deployment with consumer off, saturation with exposed versions, and rollback/drain. Keep the documented bounded retries/rate/observed outcome for genuine purge work.

### G1-06 — Medium: the new server deadlines need a concrete bounded execution/lock policy

**Contract:** §3 120-second hash worker; §4.1 line 115 2.5-second ticket deadline/one-second recovery; §11 ownership. **Evidence:** ticket/auth/database lookups are synchronous; common `repositories/base.py:46`–49 uses a five-second SQLite busy timeout, and `metadata.py:726` obtains both thread and flock locks without timeout. Existing request recovery calls the shared Qdrant client. New delivery ledger writes and descriptor pinning add contention to these boundaries. `repositories/base.py` is not in S2's allowance; `api.py` is restricted as noted above.

The numbers alone do not establish whether deadlines cover authentication, lock acquisition, SQL retries, Qdrant and source preparation or just a handler wrapper. Cancelling an awaiting coroutine does not stop an already executing blocking thread or release its resources. The new worker also needs one-process ownership, shutdown and resource admission rules distinct from request work; copying an existing `to_thread` loop is not sufficient evidence of that bound.

**Required fix:** specify deadline scope and a narrow execution strategy: bounded lock acquisition, remaining-budget DB/network operations, finite pending work, one hash owner across API workers, release/stop behavior and direct degradation when preparation is busy. State the permitted connection/lock configuration changes, or adjust the claimed server deadline to an honest bounded value consistent with the dependency budget. Add contention, timeout-then-late-completion, concurrent-worker and shutdown tests. No hashes/control-plane waits may be moved into Play to satisfy this.

## Scope and complexity decision

- **Accept the necessity of additive version/exposure state, album merge aliases, entity tombstones and one authenticated resolver.** Existing album merge deletes the source row (`repositories/albums.py:282`), and existing deletion removes the mutation journal; relying on those rows alone loses required history. The proposed `016_cdn_share_contract.sql` number and `repositories/schema.py` migration owner match the actual next migration after 015. Migration twice/interruption and old-code reads are appropriate tests. The migration runner splits SQL on semicolons, so any trigger bodies need deliberate handling, as existing version 015 demonstrates; a new SQL filename is not by itself an executable backfill.
- **Accept full-file SHA-256 as a defensible stronger choice, not as the only safe design.** A persisted opaque version with a verified file fingerprint and centrally guaranteed managed-writer invalidation could satisfy the original stat/mtime allowance without hashing. Bare size/mtime cannot. The chosen asynchronous hash avoids hashing at Play and can simplify CDN/offline identity, but worker isolation must be resolved under G1-06; automatic filesystem-move matching is optional complexity and may be replaced by explicit identity mapping. Do not add an archive or rewrite originals.
- **Accept pinning the served descriptor across an atomic replace.** A later pathname reopen can serve new bytes under an old hash. This must preserve mature Range/multipart semantics behind one owner, with descriptor close on disconnect/HEAD/error; it is not permission to rewrite the playback engine or create a generic HTTP framework. S2's delivery/content service allowances can own this implementation, with independent byte tests.
- **Accept the durable bounded purge outbox for exposed versions; reject unconditional coupling to direct-only catalog availability.** One backend lifecycle consumer and SQLite state avoid a new broker/service. At one in-flight purge and potentially 15-minute completion, throughput is limited; maintain honest queue-age/heartbeat signals and coalescing. Purge remains outside Play and never becomes the access boundary.
- **Reject the new global artist rename API as currently scoped.** Existing memberships and empty profiles need stable links, but a new global rename/name-alias system is not needed to preserve those current operations. G1-03 gives the smaller safe v1 and the requirements if the coordinator intentionally chooses the larger product change.
- **Ownership is mostly concrete, but not currently executable as a whole.** Existing web/iOS production paths in the allowance match the checkout; listed TrackDetail/ArtistDetail, share modules and CDN tests are future files. Test names for current media-ticket/closed-access, coordinator/scheduler/cache and hook/lock-screen/patch suites exist. The recipe's root `venv/bin/python` is an example to resolve before use, not a verified interpreter in this review. Required fixes must update the exact allowlists before worker dispatch; never expand them implicitly or let a junior touch dirty composition roots. Broad deploy.sh remains prohibited.
