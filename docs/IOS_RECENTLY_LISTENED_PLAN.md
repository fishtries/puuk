# iOS Home: Recently listened — задание на реализацию

Статус: план, код функции ещё не реализован. Дата: 2026-10-31.

## Результат

На главной iOS появляется горизонтальная секция `Recently listened`: до 20 разных недавно прослушанных треков с приоритетом свежести и разнообразия исполнителей, альбомов и жанров.

Порядок: `Your Mix` → `Genre Mixes` → остальные подборки, если они появились к моменту реализации → `Recently listened` → заголовок `Tracks` и общий список библиотеки. Новая секция — последняя среди подборок в `ListHeaderComponent`. Не помещать её в footer после пагинируемого списка библиотеки.

Пожелание пользователя: обновлять реже. Согласованный минимальный интервал обновления — один час. Никакого обновления после каждого прослушивания.

## Перед началом

1. Прочитать корневой `AGENTS.md`, `app/ios/puuk-ios/AGENTS.md`, skills `puuk-ui`, `puux-ux`, `docs/design/DESIGN.md` и `docs/design/ios.md`.
2. Перед написанием кода прочитать документацию Expo SDK 58 по требованию локального AGENTS.md: https://docs.expo.dev/versions/v58.0.0/ . Проверять документацию только нужных API.
3. Выполнить `git status --short` и прочитать текущие версии затрагиваемых файлов. В репозитории много незавершённых изменений, включая HomeScreen, API cache и поддержку нескольких артистов. Сохранить их; не делать reset, checkout или массовое форматирование.
4. Реализовать задачу локально. Деплой и сборка на сервере в это задание не входят.

Пути клиента далее относительно `app/ios/puuk-ios/`.

- `features/catalog/GenreMixesSection.js`: ориентир по карточкам, отступам и заголовку. Его глобальный memory cache не копировать: для истории нужна изоляция аккаунтов.
- `shared/media/CoverImage.js`: существующий компонент обложки.
- `shared/domain/trackAdapter.js`: `normalizeTrack`, `getTrackId`, `areTrackIdsEqual`; использовать их вместо новых несовместимых правил ID.
- `shared/api/apiCache.js`: `fetchCatalogWithCache`, `getCachedCatalog`, кэш на диске и в памяти, TTL, дедупликация запросов, изоляция по server/user и очистка при logout.
- `shared/api/api.js`: `authFetch`, `SERVER_URL`, функции авторизации и подписка на её изменения.
- `brain/routers/user_content.py`: `GET /api/history?limit=100`, ответ — массив сериализованных треков.
- `brain/repositories/interactions.py`: история уже исключает повторные track ID и сортируется по `played_at DESC, id DESC`.

- `hooks/usePlayerController.js`: запись истории уже есть. Массив `history` внутри контроллера служит навигации плеера; он не является источником новой секции.

Новый backend endpoint, миграции, Qdrant и изменение определения «прослушано» не нужны. Использовать текущий серверный факт записи истории.

## Шаг 1. Получение и кэш истории

Создать `shared/api/history.js` с функцией загрузки истории для главной.

- Endpoint: `/api/history?limit=100`.
- Ключ кэша: отдельный стабильный ключ, например `recently-listened-v1-limit-100`.
- TTL: именованная константа `RECENTLY_LISTENED_TTL_MS = 60 * 60 * 1000`, передавать явно. Не менять общий `DEFAULT_TTL_MS.history`, поскольку это влияет на другие потребители.
- Использовать `fetchCatalogWithCache`, передавая явные `userId`, `serverUrl`, `signal`, `ttlMs` и обработчик кэшированных данных при необходимости.
- Проверить фактические callbacks и контракт cache helper перед использованием. Он кэширует ответ API; нормализацию и выборку выполнить одинаково для кэша и сети.
- Ответ обязан быть массивом. Некорректный ответ считать ошибкой; не превращать его в успешную пустую историю и не затирать им хорошие данные. Если текущий cache helper требует небольшого расширения для валидации до записи, сделать минимальное обратно совместимое расширение и покрыть его проверкой.
- Каждый объект нормализовать через `normalizeTrack(raw, { serverUrl })`, невалидные треки отфильтровать.
- Не ограничивать историю текущей загруженной страницей библиотеки: недавно прослушанный трек может отсутствовать в `HomeScreen.tracks`.
- Пустой успешный ответ тоже кэшировать на один час.

## Шаг 2. Детерминированный отбор

Создать чистую функцию в `features/catalog/recentlyListenedSelection.js`, например `selectRecentlyListened(tracks, limit = 20)`.

Функция не делает запросов, не меняет входной массив и не использует случайность или текущее время. Вход уже отсортирован сервером от новых прослушиваний к старым. `played_at` оставлять метаданными; не пересортировывать даты на клиенте.

Алгоритм первой версии:

1. Исключить невалидные ID и дубли по `String(getTrackId(track))`, сохранив первое вхождение. Число `0` — валидный ID.
2. Первый валидный трек всегда первый в результате.
3. Для каждого следующего места рассматривать оставшихся кандидатов с менее чем двумя уже выбранными треками того же основного исполнителя. Если таких кандидатов нет, снять ограничение для заполнения оставшихся мест.
4. Если среди доступных есть треки другого основного исполнителя, чем у предыдущей карточки, выбирать только среди них. Затем аналогично предпочитать другой известный альбом. Не считать отсутствующие метаданные совпадением.
5. Среди оставшихся выбрать минимальный score: `originalRank + 12 * artistCount + 6 * albumCount + 3 * genreCount`. `originalRank` — индекс в исходном списке после дедупликации, counts — число уже выбранных треков с таким известным ключом. При равенстве побеждает меньший originalRank.
6. Повторять до `min(limit, число валидных уникальных треков)`.

Так свежесть учитывается в каждом выборе, а ограничения постепенно ослабляются при однообразной истории. Значения коэффициентов — стартовое предложение этого плана, хранить именованными константами.

Ключи метаданных:

- Основной исполнитель: первый валидный credit из `artists`; использовать его ID. При отсутствии credits — нормализованная строка `artist`. Не разбирать имена по запятым, `&` или `feat.`. Поддержку нескольких артистов сохранить.
- Альбом: `album_id`; fallback — нормализованное название альбома вместе с ключом исполнителя. Не объединять разные релизы только потому, что они называются `Greatest Hits`.
- Жанр: нормализованное непустое поле `genre`. Не вводить таксономию жанров и дополнительные запросы. `auto_genres` в первой версии не нужен.
- Неизвестное имя/жанр/альбом, включая штатные placeholders, считать отсутствием ключа. Отсутствие ключа не повышает counts и не создаёт общую группу «unknown».

Уточнение смысла: «недавние» здесь — последние 100 уникальных треков серверной истории. Календарного ограничения в 7/30 дней нет; не добавлять его без отдельного требования.

## Шаг 3. Редкое обновление

Вынести управление данными в `features/catalog/useRecentlyListened.js`, чтобы UI не управлял сетевыми гонками.

- При первом открытии авторизованной главной без кэша выполнить запрос.
- При открытии/возвращении на главную сразу показать кэш. Если ему меньше одного часа, сеть не вызывать. Если TTL истёк — сделать один фоновый запрос, сохранив карточки на экране.
- При возвращении приложения из background проверять TTL только если Home сейчас в фокусе. Использовать существующее React Navigation состояние фокуса, проверив поведение вложенного tab navigator.
- Само истечение TTL не запускает запрос: таймеров и polling нет. Оставленная открытой главная не перестраивается каждый час.
- Не подписываться на смену трека, запись истории или `PUUK_REFRESH_RECOMMENDATIONS`. Не делать принудительный refresh при каждом tab press или scroll-to-top.
- Одновременные focus/foreground события должны объединяться в один запрос через существующий cache helper.
- При ошибке оставить кэш; без кэша скрыть секцию после завершения загрузки. Не показывать модальный alert.
- После неудачного запроса выдерживать минимум 60 секунд до новой попытки при следующем подходящем событии. Не создавать таймер retry. Учитывать cooldown при remount в рамках процесса; хранить его по server/user рядом с загрузчиком. Ошибка не продлевает TTL успешных данных.
- При смене аккаунта немедленно убрать карточки предыдущего пользователя и загрузить namespace нового. При logout показать отсутствие секции и отменить запрос.
- Отмена и проверка актуальности нужны для всех асинхронных результатов, включая чтение дискового кэша. Поздний ответ старого аккаунта не меняет UI и не записывается в namespace нового.
- Повторная авторизация того же пользователя не требует запроса при свежем кэше.
- Сохранять горизонтальный offset при обычном rerender и возврате на вкладку. Не задавать списку key по текущему треку, loading или времени загрузки. При смене пользователя offset сбрасывается.

Если для защиты от гонок необходим небольшой объект состояния на namespace, держать его в модуле загрузки истории. Не строить новый универсальный cache framework.

## Шаг 4. Карточки и секция

Создать `features/catalog/RecentlyListenedSection.js`.

Предлагаемый контракт: `tracks`, `isLoading`, `currentTrack`, `isPlaying`, `onPlayTrack`, `onPressEllipsis`. Получение данных остаётся в hook; карточки не знают об авторизации и сети.

- Заголовок точно `Recently listened`, стиль согласован с `Genre Mixes`.
- Горизонтальный `FlatList`, без индикатора прокрутки; стабильный key по каноническому ID.
- Начальные размеры: карточка/обложка 140 pt, расстояние 14 pt, боковые поля 20 pt, скругление 14 pt — как у соседней секции. Не менять соседние секции ради совпадения.
- Под обложкой название и исполнитель. Длинный текст обрезается; VoiceOver получает полные строки. Не отключать системное масштабирование шрифта.
- Использовать существующий `CoverImage` и его fallback. Ошибка обложки не меняет размер карточки.
- Тап вызывает `onPlayTrack(track)` ровно один раз. Это запуск отдельного трека через действующую логику, с подбором похожих; не передавать всю ленту в `onPlayTrackList`.
- Текущий трек определять через `areTrackIdsEqual`. Показывать компактный индикатор с различием playing/paused, например иконку и доступную подпись. Не добавлять постоянно анимирующийся эквалайзер.
- Стандартное меню открывать отдельной кнопкой ellipsis через `onPressEllipsis(track)`; нажатие меню не запускает воспроизведение. Область нажатия не менее 44×44 pt, доступное название с названием трека.
- Карточке задать button role и доступное название «Воспроизвести [название], [исполнитель]» в принятом в приложении языке accessibility.
- Press feedback взять из существующего UI. В первой версии достаточно изменения opacity; декоративные каскадные анимации не нужны.
- Без кэша при первой загрузке показать три статичные skeleton-карточки; не добавлять shimmer. При фоновом обновлении skeleton не заменяет контент.
- Пустой результат: вернуть `null`, включая заголовок и отступы. Пустая секция не занимает место.

2. В header после всех подборок добавить `RecentlyListenedSection`, затем оставить существующий `Tracks` и основной список.
3. Передать уже доступные обработчики и состояние плеера. Не менять playback controller, очередь и backend history logging.
4. Обновить зависимости `useMemo`/`useCallback`, чтобы данные, меню и playing state не застывали в старом header.
5. Не оборачивать главный вертикальный `FlatList` в дополнительный вертикальный ScrollView. Сохранить пагинацию библиотеки, scroll-to-top и нижний отступ под мини-плеер.
6. Если существующий `onAddToPlaylist` влияет на маршрутизацию меню, проверить фактический контракт HomeScreen и передать согласованный обработчик, не создавая отдельное меню для новой секции.

Использовать существующий Jest и fake timers/подмену часов. Не обращаться к рабочему API или базе из автоматических тестов.

- Пустой вход, один трек, короткий список, больше 20 треков.

- История одного исполнителя/альбома заполняет ленту без дублей и зависания.
- Отсутствующие метаданные и несколько артистов; одинаковые названия альбомов разных артистов не сливаются.
- Контрольный fixture с вычисленным ожидаемым порядком для score и fallback правил.

### Данные и lifecycle — API/hook tests

- Холодный старт: один запрос с `limit=100`; нормализация полей.
- Свежий кэш, включая `[]`: повторные focus/foreground/remount не делают запрос.

- Ошибка/неправильная форма ответа не уничтожает хороший кэш.
- Смена user/server и logout во время чтения кэша или сети не показывают чужие данные.
- Данные сохраняются между remount; по возможности использовать инфраструктуру существующих `apiCache.test.js`, не дублировать все тесты общего кэша.

## Критерии готовности и отчёт

- Секция стоит последней среди подборок и показывает только серверную историю текущего пользователя.
- До 20 уникальных карточек, первый трек самый свежий; отбор разнообразный и воспроизводимый.
- Нет обновлений на каждое прослушивание, polling или фонового таймера; TTL секции один час.
- Нет утечки данных между аккаунтами, исчезновения кэша при временной ошибке и конфликтов вложенного скролла.
- Воспроизведение и меню используют действующие обработчики; остальная главная работает как прежде.
- Изменения ограничены iOS и необходимыми точечными дополнениями к его кэшу. Новые зависимости не добавлены.
- В отчёте перечислить изменённые файлы, команды проверок и результат, пределы проверки на устройстве, известные отклонения от плана. Проверить итоговый diff только своих изменений; не включать чужие изменения в отчёт как свои.
