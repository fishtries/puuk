# Ревью выполнения плана пословных текстов

Дата: 2026-11-10. Проверены текущие файлы рабочего дерева и локальные снимки. Production и устройство iOS в этом ревью не проверялись. В ходе исходного ревью код и исходные пользовательские данные не изменялись. Последующее исправление описано ниже.

Вывод: основная интеграция реализована, но утверждение «все пять этапов выполнены» преждевременно. До выпуска нужны исправления экспорта, времени подсветки, привязки аудио и инструментов восстановления.

## Подтверждённые проблемы

### 1. P1 — экспортёр изменяет ручные тайминги

`scripts/lyrics/export_word_lyrics.py:140–149,182–193` выравнивает начала слов/строк по предыдущим и при необходимости создаёт интервал в 1 ms. Признак `locked` не защищает границы. Также есть автоматическое обрезание по длительности и расширение округлённого нулевого интервала (`110–118`). Это противоречит требованию сохранить разметку и диагностировать конфликт вместо исправления наугад.

В `/home/fish/psychoboost-aligned.json` слово ID 606 имеет `locked: true`, интервал 198.10676017544898–198.44006003367207 s. В `data/word_lyrics/psychoboost.json` оно стало 198839–198840 ms. ID 605 перед ним начинается в 198.83860859227315 s: именно конфликт порядка запускает сдвиг. Исходная граница могла быть ручной правкой пользователя; ревью не оценивает её акустическую правильность. Дефект — скрытое изменение при переносе.

Проверка причины: SHA-256 исходного JSON совпал с `sourceChecksum` provenance. Повторное преобразование в памяти воспроизвело тот же сдвиг ID 606; все строки и слова повторного результата совпали с сохранённым снимком. Полная revision отличается из-за определения общей длительности текущим окружением: 244831 вместо 244872 ms. Поэтому не заявляем полное воспроизведение байтов документа.

Всего относительно исходного экспорта в сохранённом Psychoboost изменены два слова: ID 484 (начало +123 ms) и ID 606 (ручная правка). Исправление: исключить скрытую коррекцию, вернуть диагностику конфликта и согласованный fallback/остановку экспорта; добавить тест сохранности locked и тест инверсии начал. Не менять сами пользовательские исходники. Затем пересобрать и повторно проверить снимки.

### 2. P1 — визуальное время обновляется слишком редко для коротких слов

`hooks/usePlayerController.js:404` не задаёт updateInterval. Установленный `expo-audio/src/ExpoAudio.ts:99` использует 500 ms по умолчанию. `AppleLyricsView.js:685–707` передаёт непосредственно currentTime в рендер слов. Интерполяции или другой подписки для пословного времени здесь нет.

Короткое слово может целиком попасть между двумя status-событиями и ни разу не стать активным. Это отдельная ошибка воспроизведения таймингов, независимо от качества модели. Jest с вручную заданным currentTime её не проверяет.

Исправление: реализовать привязанный к движку визуальный clock либо обоснованную измерениями частоту обновления; проверить короткие интервалы, паузу, buffering, seek, скорость и foreground на устройстве. Не ограничиваться уменьшением периода без проверки нагрузки: сейчас каждый currentMs пересоздаёт список строк.

### 3. P1 — проверяется сохранённый путь аудио, а не текущий файл трека

`brain/repositories/tracks.py:762–778` делает stat по `track_word_lyrics.file_path`. Текущий `tracks.file_path` не сверяется. Импортёр дополнительно позволяет произвольный `--audio` вместо файла трека.

В изолированной БД воспроизведено: импорт снимка, перевод tracks.file_path на другой существующий файл при сохранении исходного — get_track_word_lyrics продолжает отдавать старый снимок. Можно показать тайминги от другого аудио.

Исправление: разрешать и сверять фактически воспроизводимый файл текущего track_id; ограничить/проверить override; при смене привязки не отдавать старую разметку. Добавить регрессионный тест с двумя файлами.

### 4. P2 — повторный импорт не восстанавливает инвалидированную stat-подпись

`scripts/lyrics/import_word_lyrics.py:114` возвращает noop только по revision + is_active. Если изменился mtime при неизменных байтах, чтение отказывает, а повторный импорт даже после успешной SHA-256 проверки не обновляет подпись.

Воспроизведено в отдельной временной БД: `REIMPORT_AFTER_TOUCH noop_identical_revision`, после этого `get_track_word_lyrics(...) is None`.

Исправление: no-op только при совпадающей привязке и актуальной подписи; после подтверждения хеша обновлять подпись. Проверить touch и перенос файла отдельно от изменения аудиобайтов.

### 5. P2 — заявленный откат не реализован в CLI, процедура доставки неполна

`scripts/lyrics/import_word_lyrics.py:177–184` требует --input и не определяет --track-id/--deactivate. Команда из отчёта не может выполниться, хотя функция репозитория для отключения существует. Резервный JSON оборачивается в previous_record; документированного CLI восстановления этого формата нет.

`brain/deploy.sh:100,122` доставляет brain и tg_music_bot. Корневые scripts/lyrics и data/word_lyrics таким запуском не доставляются. Поэтому приведённых команд выпуска недостаточно для чистого сервера.

Исправление: реализовать и проверить отключение/восстановление; описать точную доставку CLI и снимков, окружение Python и команды dry-run/apply. Подтвердить откат на временной БД. Это не поручение выполнить production-деплой в ходе ревью.

### 6. P2 — пересечения между строками теряют подсветку

`AnimatedLyricLine.js:174` вычисляет состояния слов только при isActive. В `AppleLyricsView.js:690` активна ровно одна строка. При допустимом пересечении двух строк начало следующей отключает подсветку ещё звучащего слова предыдущей.

Исправление: отделить строку фокуса автоскролла от определения активных слов; добавить компонентный тест с перекрывающимися строками. Тест функции getWordState внутри одной строки недостаточен.

### 7. P2 — backend не проверяет сохранённый документ при выдаче

`brain/repositories/tracks.py:782–785` выполняет только json.loads. Не проверяет schemaVersion, trackId, revision или ограничения документа. Временная запись с schemaVersion=999 была возвращена как снимок. Непустой невалидный объект также подавляет обычный поиск текста в lyrics_service.

Исправление: валидировать документ при чтении (либо использовать проверенный кеш по revision), неподдерживаемые/испорченные данные превращать в null с диагностикой; тестировать fallback на LRC/plain и отсутствие падения всего endpoint.

## Что проверено

- `brain/venv/bin/python -m pytest brain/test_word_lyrics.py brain/test_tracks_etag.py brain/test_closed_access.py -q`: **27 passed**.
- Из iOS-каталога `npm test -- --runInBand components/fullplayer/lyrics/__tests__/`: **65 passed**.
- Дополнительные проверки проблем 3, 4, 7 выполнены в отдельной временной БД с явно заданным PUUK_DB_PATH. Рабочая БД не изменялась.
- Сравнены исходный экспорт Psychoboost, provenance и итоговый документ; преобразование повторено в памяти.
- Локальная brain/puuk.db прочитана только в режиме SQLite mode=ro: записи трёх снимков и provenance присутствуют. Это не подтверждает наличие снимков на сервере.

Зелёные тесты подтверждают покрытые сценарии, но не сохранность каждого ручного интервала, реальное время подсветки или готовность отката. В текущем backend-наборе тесты также зависят от записей предыдущих тестов; успешная замена с backup не проверяет откат транзакции при сбое.

пока нельзя. Обязательная приёмка на устройстве остаётся открытой.
