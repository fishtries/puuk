# Проверка записи при импорте Spotify

## Поведение

Spotify используется для метаданных. Поиск аудио идёт по категории songs YouTube Music;
обычные YouTube-видео и Piped не используются как автоматический fallback.

До скачивания проверяются название, все исполнители, вид версии и длительность
(допуск 2%, минимум 2 секунды, максимум 5). Для explicit-трека требуется положительный
признак explicit у кандидата; отсутствие слова clean не считается доказательством.
ISRC используется только как поисковая подсказка. Популярность не отменяет проверки.

После получения extractor metadata снова проверяются video ID, длительность, признаки
трансляции и нежелательной версии. После конвертации проверяется длительность MP3.
Теги исходного Spotify-трека записываются только в подготовленный файл.

Файл содержит TXXX:PUUK_SOURCE_V1 с версией политики, Spotify URL и данными кандидата.
Повторный импорт использует файл только с таким подтверждением и подходящей длительностью.
Старый WOAS сам по себе недостаточен: прежний загрузчик ставил его и на неверное аудио.
Существующие файлы не перезаписываются; при коллизии имени сохраняется отдельный файл.
Это не автоматическое исправление уже импортированной библиотеки.

## Отказы и границы

Получение Spotify-метаданных ограничено 180 секундами, поиск/скачивание каждого трека —
180 секундами, обработка набора — бюджетом 30 минут (проверяется между треками).
При отмене/таймауте убивается группа процессов, включая ffmpeg. Временная папка очищается.
Успешные элементы публикуются после обработки набора. При отмене до публикации подготовленные
файлы удаляются. Перезапуск бота не возобновляет импорт: долговечная очередь — отдельная работа.

До трёх прошедших проверку кандидатов пробуются последовательно. Сбой одного трека не
отменяет остальные. Бот показывает причины пропусков, а не выдаёт подбор похожей версии за успех.

Прямая ссылка YouTube и ручной выбор видео в поиске сохраняют прежнюю семантику:
скачивается выбранное видео. Строгая проверка относится к автоматической подстановке
аудио при импорте Spotify.

Метаданные не доказывают содержимое звука. Неверная маркировка explicit, скрытая цензура
или инструментальная подмена с идентичными названием, исполнителями и длительностью
могут потребовать аудиосравнения/прослушивания. Гарантии распознавания таких случаев нет.

## Проверка 2026-11-15

- 66 изолированных тестов: подбор версий, explicit unknown/false, все исполнители,
  сохранность старых файлов, параллельные импорты, частичный успех, отмена, реальный timeout дочернего процесса.
- Живой каталог нашёл альбомные explicit-кандидаты для «завтра» (Wlz68h2oAVQ),
  «танцуй» (z3mEsgaBrR8), «охота на уток» (MdB8nuQLSjw).
- Все три записи реально скачаны во временные папки: «завтра» — 91.632 сек.,
  «танцуй» — 116.088 сек., «охота на уток» — 99.6 сек. Provenance записан;
  повторная проверка через механизм reuse прошла для каждого файла.
  Содержимое вокала и отсутствие скрытых вырезаний на слух не проверялись.
- Live-проверка spotDL save для Spotify не завершилась за внешний тестовый лимит 60 секунд.
  Поэтому полностью успешный путь от ссылки Spotify до публикации на реальной сети пока
  не подтверждён. Тесты orchestration используют подставленные результаты метаданных.
- Production-код и музыкальные файлы не изменялись. Проверка серверной SQLite и ID3 была read-only.

Запуск локальных тестов (не включать test_spotify.py/test_ydl.py: это старые сетевые скрипты):

```
brain/venv/bin/python -m pytest -q tg_music_bot/test_source_selection.py tg_music_bot/test_download_isolation.py tg_music_bot/test_audio_tags.py tg_music_bot/test_multi_artist_import.py tg_music_bot/test_bot_phase4.py
```

## Обновление: независимый источник и долговечная очередь

Актуальное поведение заменяет описанные выше ограничения по восстановлению:

- После неудачных кандидатов YouTube Music выполняется независимый поиск SoundCloud
  через yt-dlp, до 5 результатов и 3 подходящих попыток. Используются структурированные
  artist/track/duration. Имя загрузившего не считается исполнителем. Unknown explicit
  остаётся unknown: SoundCloud-кандидаты без положительного признака explicit не подходят
  для explicit Spotify-треков. Поэтому резервный источник не гарантирует нахождение
  explicit-записей. Это ограничение качества данных, проверки ради доступности не ослаблены.
- Spotify-импорт в библиотеку через бот сохраняется в отдельной SQLite-очереди.
  Режим отправки файлов в чат и прямые ссылки сохраняют прежний способ запуска.
- `PUUK_DOWNLOAD_QUEUE_PATH` задаёт путь; по умолчанию `tg_music_bot/state/downloads.sqlite3`.
  Каталог state исключён из git и синхронизации деплоя.
- Один обработчик держит flock на весь срок жизни. Только он восстанавливает running
  после остановки. Второй обработчик той же очереди не запускается. Это модель одного
  владельца на Linux, а не распределённая очередь.
- Снимок метаданных Spotify сохраняется атомарно в `state/imports/<id>/metadata.spotdl`.
  Проверенные файлы публикуются по одному. После остановки повтор использует снимок
  и проверенные receipts готовых файлов; незавершённый трек обрабатывается заново.
- До 100 активных импортов. Для сетевых/процессных ошибок — до 3 попыток с задержками;
  ошибки валидации автоматически не повторяются. История успешных импортов и снимки
  старше 30 дней удаляются при следующем запуске обработчика.
- `/downloads` показывает последние 10 своих операций; `/retry номер` возвращает
  частичный или неуспешный импорт в очередь. Готовые файлы проходят reuse, ошибки
  проверяются заново. Доступ проверяется также перед выполнением очередной операции.
- Недоставка статуса в Telegram не инициирует повтор скачивания. Операции индексации
  после восстановления снова вызываются с существующими файлами через текущий путь бота.

Проверки: 71 тест, включая эксклюзивного владельца, восстановление после остановки,
предел повторов, backoff, ёмкость, владение операцией при retry, переиспользование снимка
и завершённых треков, переход ко второму провайдеру без ослабления проверок.
SoundCloud на реальной сети и восстановление production-процесса не испытывались.
Изменения не развёрнуты; известная задержка spotDL metadata остаётся ограниченной
таймаутом, а не считается устранённой.
